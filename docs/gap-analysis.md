## 0. プロジェクトの定義（あるべき姿）

> **工房の作業台に置かれた、手作りの地球儀ミニチュア。
> 見た瞬間に「どこ」か分かり、しばらく眺めると「生きている」と分かる。**

4つの柱に分解する。

1. **物としての説得力** — 樹脂の海、塗装した陸、綿の雲、植毛の緑、真鍮の金具。
   宇宙に浮かぶ惑星のCGではなく、机の上に実在する物体として撮影された絵。
2. **一目で「どこ」か分かる** — 地形・気候・植生・建造物が実座標。ただし
   **地理の教科書ではなく土産物の地球儀**。正確さではなく「その地域といえば
   コレ」という記号の強調がゴール。アマゾン＝密林と大河、サバンナ＝アカシアの傘、
   地中海＝糸杉、北欧＝トウヒ、砂漠＝砂丘。
3. **生きている** — 四季（1分＝1年）、風と雲、昼夜と街の灯り、船・飛行機、
   噴火、台風。
4. **携帯で動く** — 単一品質構成、シャドウマップ無効、ドローコール抑制。

### 2-1. 森林密度（立体角あたり、惑星全体を実測）

| **コンゴ盆地** | **0** | **10,207** | チベット | 315 | 159 |
| **ボルネオ** | **678** | **11,054** | シベリア中央 | 88 | 8,008 |
| 西欧 | 394 | 7,945 | 米東部 | 521 | 6,361 |
| パンパ | 0 | 7,402 | 米グレートプレーンズ | 549 | 5,026 |
| ブラジル南東部 | 0 | 4,697 | インド(ガンジス) | 274 | 4,249 |
| 日本 | 446 | 2,847 | サヘル | 0 | 911 |

**熱帯雨林3つが惑星の上位3位**になり、いずれもアラスカを上回る。

### 2-2. 原因1：森林判定が気候ではなく標高で決まっていた（解決済み）

`species.ts` の森林条件にあった `height >= SEA_LEVEL + 0.02` が、
気候的に適地である陸地候補の**75%を単独で落としていた**。
旧・架空地形時代（陸＝丘）の名残。実標高データでは陸の大半が平坦な低地。

**撤廃済み。** 陸地レイヤの標高ゲートは全廃し、判定は「海面より上か」だけ。
海岸の砂浜帯（`COAST_WIDTH` = 0.006）を避ける程度の余裕すら広すぎる
——コンゴ盆地の平均海抜がちょうど 0.007 だから。

### 2-3. 原因2：badlands がノイズのままだった（解決済み）

陸地候補の 19.4% が `badlandsAt`（純粋なfbmノイズ、地理情報ゼロ）で
植生を拒否されていた。**ケッペンB群・Ds群駆動に変更済み**
（`KOPPEN_BADLANDS`）。メサはコロラド高原とゴビに立ち、サハラは砂丘になった。

### 2-4. 原因3：絶対数が足りなかった（解決済み）

惑星全体で2,700個弱。**31,627個に増やし、1個あたりを小さくした。**
森林の最小間隔は林冠密度で可変（熱帯雨林 0.0065／疎林 0.017）。

### 2-4b. 途中で見つかった上流のバグ2件（いずれも解決済み）

G1に着手して初めて分かったが、**「そこが陸かどうか」を決めていたのは
標高ゲートだけではなかった。**

1. **符号付き中間レリーフノイズが平地を海に沈めていた。**
   `heightAt` の `midRelief * 0.145 * landMask` は振幅±0.021。海抜が
   数千分の一しかない盆地では自分の海抜の数倍あり、下向き半分が
   そこを水没させていた。**標高ラスタ上では100%陸地のコンゴが57%水没、
   サヘル62%、シベリア中央66%。** landMask の下端を `SEA_LEVEL - 0.03`
   から `SEA_LEVEL` に上げて解決。

2. **陸/海のグレースケール閾値 145 が最下位の陸地帯を切っていた。**
   ラスタを直接測ると、既知の浅海（北海）は最大143、既知の平坦な内陸
   （コンゴ盆地・グレートプレーンズ）は147から始まる。**144〜145 が
   世界で最も平坦な低地の値** —— アマゾン盆地の60%、パンパの73%、
   西シベリア平原の83%がここにいて、全部が海として読まれていた。
   **143に変更。** 面積加重の陸地比率は 23.8% → **28.0%**（地球の実際は約29%）。
   あわせて陸の第一段を砂浜帯より上に持ち上げた（`ELEVATION_LAND_FLOOR`）。
   でないと「非常に低いだけの大陸」が丸ごと砂浜色に塗られる。

### 2-4c. 熱帯雨林が茶色く塗られていた（解決済み）

`biomeColor` のラテライト（`tropicalSoilColor`）が `tropical`（＝実質的に
緯度のみ）でゲートされており、**降水量と正確に反比例して赤土を塗っていた。**
林冠が閉じている赤道直下で最大強度0.65、20°南のセラードでゼロ。
アマゾンとコンゴが泥色で隣のサバンナが緑という逆転。乾燥度でも
ゲートして解決（セラードとサヘルの見た目は不変）。

### 2-5. 海の波

- 波は**静止バンプテクスチャの横スクロール** = 模様全体が自転軸まわりに剛体回転。
- 頂点変位の振幅は最大 **0.0019**（半径2の球に対し1/1000）。
- 波長0.45に対し海メッシュは76×44（赤道で1辺0.165）＝**1波長2.7頂点**で破綻。
- ~~**海岸の白波が存在しない。**~~ → 第2弾で実装（§2-10）。

### 2-6. 降水

- **降雨は一行も存在しない。** 嵐雲は雷を光らせるが何も降らない。
- 降雪は緯度のみで判定。海陸を区別せず、気候区分を見ず、**雲と無関係**
  （快晴の空から降る）。雪片は固定方向なので**同じ場所が永遠に降雪地点**。
  塗装の雪線とは完全に独立した2系統で、積もらない。
- ケッペン区分は降水パターンの分類（f/w/s/m）そのものなのに、**降水量として
  使っていない**。

### 2-8. 川がほぼ動いていない（第1弾中に計測で判明・未着手）

`biomeColor` を全項目分解して計測した副産物。

- 流量累積の**全球最大値が242**。`strength = (ln(flow+1) - 3.4) / 2.5` は
  青くなるのに flow > 29、最大強度に flow > 364 を要求するので、
  **惑星上のどのセルも最大強度に届かない。** 何らかの川が見える陸地セルは0.68%。
- 原因は D8 の落とし口探索が `<` の厳密比較で窪地埋めがないこと。
  **陸地セルの12.6%がシンク**になり、平地で流れが止まって本流が育たない。
- アマゾン箱の最大流量22、コンゴ箱33。**どちらにも川のピクセルが1つもない。**

**関連する時限爆弾**: `deltaCoast = 1 - smoothstep(elevation, 0, 0.05)` は
アマゾンで0.907、コンゴで0.845。いま `riverStrength` が0だから何も起きて
いないだけで、水系を直した瞬間に堆積扇の砂色 `#a99568` が最大0.50の割合で
**盆地全体を3,000km内陸まで塗る。** 直すときは `deltaCoast` を
terracedElevation ではなく生の海抜（例 `smoothstep(h, SEA_LEVEL, SEA_LEVEL+0.008)`）
で取ること。G27に着手する人へ。

### 2-10. 白波は「深さ」ではなく「岸からの距離」（第2弾）

最初の実装方針（`SEA_LEVEL` より浅い水深でゲートする）は**間違い**だった。
大陸棚は幅全体が浅いので、深度0.013の帯で**北海・アイリッシュ海・スンダ棚・
タイランド湾がまるごと白くなった。** 平面展開図に出すまで気づけない類の失敗。

正しい量は**海岸線からの距離**。陸マスクに対する2パスのチャンファー距離変換
（1 / √2、経度の継ぎ目で巻く）で距離場を作り、そこから帯を描く。
幅と強度は `coastCliffiness` と沿岸方向の中周波fbmで変え、`coastlineJitter`
をテクセル単位で加えて塗装された海岸線と一緒に揺らす。

実測（2048幅）: 白波ピクセルは全球の1.15%、東南アジア12.6%、地中海10.6%、
英国6.7%、太平洋中央0.60%（島のみ）、大西洋中央0.00%、サハラ0.00%。

### 2-11. 都市（第2弾）

28都市 → **186都市＋17の都市回廊**（`URBAN_FEATURES`）。回廊は東海道・山陽・
米北東部・ライン=ルール・ロンドン=マンチェスター・ガンジス・ナイル・長江
デルタ・珠江・インダス・ジャワ北岸・サンパウロ=リオ等。

**`urbanAt(dir)` が単一の真実。** 昼の灰色塗装・夜の灯り・植生の伐採が全部
これを読む。2系統が別式で「都市はどこか」を計算するのは §2-6 の雪線／雪片の
分裂と同じ失敗になるため。

- 市街地面積は陸地の1.27% → **2.40%**（球の0.74%）。モンテカルロ30万点。
  パッチ半径を `0.014 + size*0.026` → `0.0085 + size*0.0135` に縮めて調整。
- **性能は7倍の要素数で逆に速くなった**: 900k回の `urbanAt` が117ms → **68ms**。
  5°×5°のバケットグリッドをモジュール読込時に1回作る。
  ページ読込時間は同一ビルドで79秒と115秒に振れて使い物にならないので、
  関数を直接ベンチした。
- 植生の伐採は`urbanAt`の生値では足りない。塗装用に調整された値をそのまま
  使うと**核でわずか27%の間引き**にしかならず、灰色の上に木が立ったままだった。
  2.6倍して核を飽和させ、28都市で計測: 中心0.012rad以内 **-80.0%**、
  0.012–0.022radの環 -30.1%、0.06rad超 -0.2%、惑星全体の森林 -0.4%、
  草は -37.5%（公園として残す）。
  **計測は都市サイズの帯で行うこと** — パッチは東京でも約0.018radしかなく、
  0.03radの傘で平均すると効果が消える。

**標高ラスタは世界の大デルタを海として読む。** 回廊の候補を直接プローブした
結果: 上海=南京は21点中14点、上海=杭州18/21、カイロ=アレクサンドリア15/21、
ルール=ランドスタット14/21が `SEA_LEVEL` 未満。初稿14本のうち4本は昼に何も
塗らず夜に外洋を光らせるところだった。**経路はアトラスではなくラスタに対して
引くこと。** 同様に**186都市のうち26都市の中心座標が水ピクセル**
（ニューヨーク、ムンバイ、上海、ラゴス、ヒューストン、バルセロナ、
コペンハーゲン等）。今はパッチが隣接する陸を覆うので無害だが、
**G43/G48で建物や港を都市の正確な座標に置くと海の中に建つ。**

**`habitabilityAt` は強く熱帯寄り（未着手）。** 平面展開の夜図では
アマゾン・コンゴ・島嶼部東南アジアが欧州や米東部より明るく光る。
誰もが知る夜の地球の画像の**正反対**。都市テーブルではなく散在灯りのパスの
問題で、G47の次の実体。

### 2-12. 明暗境界は動かない（第2弾で判明）

**キーライトもカメラも固定なので、明暗境界は円盤上を掃かない。** 太陽は
カメラ軸から約55°離れており、境界は**円盤半径の約58%、反太陽側**に固定される。
地形がその線を通過していくのであって、線が地形の上を動くのではない。
夕暮れを検証する人は**左リム（＝太陽側で最も明るい）ではなくこちらを見ること。**

初版の夕暮れ帯が不可視だった原因は2つ、どちらも同じ間違い方をしていた。

1. `diffuseColor.rgb` を掛けると効果がアルベドに比例し、**境界が最も長く
   横切る面である暗い海の上でほぼゼロ**になる。
2. ドット積で幅0.08の窓は円弧にして約4°、このフレーミングで約20ピクセル。
   露出1.9のトーンマッピングで潰れる。

幅と強度を上げ、暗い海にも乗る下限を入れた。ただし**海の暖色帯は陸より
大幅に弱くしてある** — 暗い青に橙を足すと夕焼けではなく**茶色い汚れ**に
見えるため。海側はブルーアワー（寒色帯）に役割を持たせている。

**検証手法の注意**: 回転停止トグルで位相を揃えたA/B比較を試みたが、
**季節アニメーション（1分＝1年）が止まらない**ため2回のキャプチャで
北米の紅葉が別フェーズになり、85%の画素が変化して判定不能になった。
季節を止める手段が現状ない。画像A/Bをやるなら先にそこを用意すること。

### 2-14. シャドウマップ無しで雲影を落とす（レビュー第1位への対応）

**この作品には影が1つも存在しなかった。** `main.ts` で
`renderer.shadowMap.enabled = false`（実機クラッシュの犯人として切り分け済み、
復活させないこと）なのに、キーライトと球・海・台座・小物すべてに
`castShadow`/`receiveShadow` が立っていて**全部無効**だった。木は地面に、
雲は海に、陸は海面シェルに、球は机に、どれも影を落とさない。
外部レビュー（Gemini）も独立に同じ場所を指摘した。

雲影だけはシャドウマップ無しで落とせる。**雲が閉形式で動くから**である：
ノジュールの経度は `lon + zonalOmega(lat) * t` でしかなく、雲グループは
globeGroup の子なので、球の物体空間ではこれが運動の全て。デッキを一度
equirectangular に焼き、シェーダ側で**同じ式で引く位置をずらす**だけで
影が本物の雲に追従する。レンダーターゲット無し、追加パス無し、
テクスチャフェッチ1回。

- 実装は `buildCloudShadowTexture`（512×256 RGBA）。**R = 被覆、
  G = その緯度の移流速度**。G を使うのは、風プロファイルをGLSLに
  書き写すと噴煙で一度潰した「2つの式」問題の再発になるため。
  omega は緯度のみの関数なので行定数チャンネルで厳密に運べる。
- 強度は陸0.38・海0.62。**海を強くするのは意図的** — 外洋は自前の
  テクスチャをほとんど持たないので、横切る雲影が「空の下の面である」
  ことを語る主役になる。0.42では素の海色が暗く相対差が出ず、ほぼ
  見えなかった。
- **既知の近似2つ**: (1) 影は雲の真下に落とす（光源方向のオフセット無し）。
  (2) 帯の蛇行 `meanderAmplitude` を無視。最大0.085 rad（約4.9°）だが
  熱帯（20°未満）と極（75°超）ではゼロなので、このフレーミングで海が
  最も見える領域では誤差ゼロ。台風のノジュールは自分の移動フレームに
  いるため除外（閉形式が当てはまらない）。

### 2-15. 残りの影2種（完了）

**海岸の接地陰は「書いてあるが効いていない」状態だった。** 計測値：陸地全体の
平均 |AO| は **0.0040**（最大 0.16 の 2.5%）、|AO|≥0.02 は陸の 3.61% だけ。
しかも**外し方が両方向に同時に間違っていた**：

- 海岸線から3テクセル以内の陸（陸の 10.2%、80,227テクセル。この効果が存在する
  理由そのものの帯）のうち、**|AO|≥0.08 を受けていたのは 16.5% だけ**。
  崖の海岸は1テクセルで海抜0.006を超えるので、**最も影が要る場所で影が付かない**。
- 逆に、darkening を受けたテクセルの **12.9% は海岸から8テクセル以上内陸**。
  平坦な内陸は数千kmにわたって海抜0.006未満だから（コンゴ盆地の平均は0.007）。

**原因は §2-10 の白波と完全に同じ。正しい量は海岸線からの距離であって、
標高ではその距離を表現できない。**（デルタは内陸まで低く、岬は水際で高い。）
既存のチャンファー距離場に `side: 'sea' | 'land'` を足して陸側でも引けるようにし、
そこから帯を描いた。結果：**海岸帯の被覆 16.5% → 100.0%、内陸への漏れ 12.9% → 0.0%。**
幅と深さは `coastCliffiness`（実際の `coastalStep` を駆動しているのと同じ場）と
白波と同じ沿岸方向ノイズで変える。海側にも同じ理屈の遮蔽（`shoreOcclusion`）を
白波の**下に**敷いた。泡は明るいまま暗い襟の上に乗るので白のコントラストが上がる。

**方向を持たせないのは意図。** 球は固定キーライトの中で自転するので、光源方向を
焼き込んだものは回転の大半で嘘になる。海岸の隅の水は太陽がどこにあろうと空を
見込む量が減るので、方向なしの遮蔽が安い答えであると同時に正しい答え。

#### ここで踏んだ罠2つ（どちらも平面展開図でしか見つからない）

1. **`offsetHSL` は linear 空間で定数を引く。** THREE.Color は linear なので、
   linear 輝度 0.15 しかない海岸の緑から 0.24 を引くと**暗くなるのではなく黒に
   クランプする**。全大陸が**硬い黒の輪郭線**を身に着けて出てきた —— この作品が
   一貫して避けてきたデカール読みを、事故で自分から作った。
   **遮蔽は届く光を「掛ける」もので、定数を引くものではない。**
   乗算なら暗いテクセルも明るいテクセルも同じ「割合」を失うので、
   原理的にキーラインが出ない。以後この3項目は全部乗算。
2. **強い darkening を気候ラスタに直結すると、最近傍の階段エッジ（§2-9）が
   フルコントラストで描かれる。** 東南アジアが矩形の集合になった。
   **強度を下げても矩形が薄くなるだけで直らない。**
   引く「方向」を細かいノイズでワープさせること（`canopyWarp`）。境界が
   グリッド数セル分ゆらいで階段でなくなり、本当に鋭い所は鋭いまま残る。

### 2-16. 林冠の接地陰は塗装だけでは半分（完了）

`canopyAt` で塗装を暗くしただけでは足りない。**3Dで見て初めて分かったが、
31,600個のインスタンスが地面をほぼ完全に隠しているので、塗装だけ暗くしても
「木と木の間」が変わるだけで木自体は何も変わらない。**

クランプ側にも同じ陰を入れた。既存の per-clump の明度ばらつきは `rand()` 由来、
つまり**白色ノイズ**で、隣同士を無相関に振るので「平らな塊の上のスペックル」に
しか見えない。森の明暗は逆に強く**構造化**されている：閉じた林分の底は隣が
屋根になるので暗い、同じ林分の縁は各樹冠が空を見るので明るい、屋根の上に
突き出た emergent が最も明るい。

3項（すべてインスタンス色に載るだけでジオメトリもマテリアルもドローコールも増えない）:
`canopyAt`（林冠の閉じ具合、間隔を決めているのと同じ場）×
サイズ階層由来の「埋もれ具合」（小さいクランプが林床、大きいものは光を保つ）×
**空間的に連続な**パッチノイズ（これが影とスペックルの違いそのもの。周波数は
クランプではなく林分のスケール）。

計測（塗装側）：閉じた林冠の地域が **6〜11% 暗く**（コンゴ -10.9%、米東部 -10.0%、
アマゾン -8.3%）、砂漠と高原は **0.1% 以内で不変**（サハラ 0.0%、豪州内陸 -0.0%、
チベット -0.1%）。海側の変化は面積の 2.4%、平均 -0.0007。

### 2-17. 雲の質感（G8、完了）

**「同じ丸い塊」も計測できる。** 着手前：ノジュール830個、サイズの
90/10パーセンタイル比 **2.58**、そして**惑星上の全ノジュールの 63% が中央値の
±30% 以内**。1つの粒径は1つの材質に見え、同じ大きさの球でできた材質は
綿ではなく発泡スチロール。

ちぎった綿は逆の統計を持つ —— 少数の大きな塊、それに寄りかかる肩、縁から
むしれた大量の粒。クラスタ内でノジュールに順位を付け（後のものほど小さく
背骨から離れる）、**局所の bulk でスケールされない**ほぼ固定サイズの房を
その外側に置いた。端では房を最後のステップより先に投げ、塊自体を落とし始めるので、
帯は「一回り小さい球」で終わらずに**ちぎれた粒に解ける**。
比 2.58 → **3.32**、±30%内 63% → **55%**（帯タイプ単体では 32〜44%）。

**引き伸ばしと櫛通しはビルド時に焼けない。ここが一番おもしろい所。**
従来の回転は法線への**最小回転**でノジュールを立てており、これは位置依存の
ねじれを持つ。だからビルド時に固定した向きは、風が帯を運ぶにつれて狂っていく
——偏西風は1分で経度1ラジアン以上動かすので、**見ている間に櫛通しがランダム
スピンへ戻る**。方位角（コンパスベアリング）はこの移流に対して不変なので、
grain を毎フレーム解決する方式にした。grain・法線・従法線からインスタンス基底を
直接書き出すので、**置き換え前より per-frame が安い**（軸角構築なし、
クォータニオン積なし、TRS compose なし）。

**コストは renderer.info で実測した（推測ではなく）**：シーン全体の
ドローコール **150 → 147**（雲の予算は3本「減った」。ノジュール変種を帯単位
ではなくノジュール単位で交互配置したら最初は+2になり、変種を1つ削って払った）。
三角形 2,605,733 → 2,649,631（**+1.7%**）。レンダーターゲット・追加パスなし、
シャドウマップ不変、**チューニング済みのハロー／フリンジと灰色の輪の対策には
一切触っていない**。

**正直に未達**: ズームすると塊は「毛羽立った綿」ではなく「滑らかな白い小石」に
見える。ここから先はセグメントを増やすか、ハロー方式を開け直すかで、
どちらも当てずっぽうでやる価値はない。

### 2-19. 雲を降水場に繋いだ（第3弾の一歩目、G7）

**§3 の「気象の発生源が一元化されていない」に初めて手を付けた節。**
`precipitationAt` は完成していたのに消費側がゼロだった。雲はその5系統のうち
一番声が大きい —— 空はケッペンを一度も読んでいなかったので、**サハラの上にも
コンゴの上にも同じ確率で雲塊が乗っていた**。

**繋ぎ方は2段。雲は動くので、「どこで雨が降るか」の2軸は別物として扱う。**

- **緯度は帯状風に対して不変。** だから「その緯度にそもそも雲が何個あるか」と
  「何型か」は、新設した `zonalPrecipitationAt`（降水場の緯度平均）に対する
  棄却で決める。
- **経度は不変ではない。** だからローカルな側は**毎フレーム、流れ着いた先で**
  読む。**帯単位ではなくノジュール単位**なので、サヘルを横切る帯は
  モンスーン側が綿のままサハラ側だけがほつれる。
  ビルド時に焼いていたら §2-17 の「焼いた向きは移流で狂う」の再演だった。

**計測（16 RNG シード × 惑星一周ぶんの時間で平均）。**
帯は10本しかないので、**どの10箇所に当たったかが規則の差より大きく効く** ——
最初に1シードで比較したときは「砂漠好きが4倍になった」と出て、同じコードが
別シードでは逆を出した。**シード1本での前後比較はこの系では意味がない。**

| 指標 | 着手前 | 完了後 |
|---|---|---|
| 陸上の雲の下の平均降水量 | 0.364 | 0.446 |
| 乾燥地の上にある陸雲の割合 | 34.8% | 24.6% |
| **熱い砂漠の雲の濃縮率**（単位面積あたり／全球平均） | **x1.82** | **x1.35** |
| 夏雨型の陸地の上の雲量（北半球）1月→7月 | — | **+27%** |
| 同（南半球）1月→7月 | — | **−55%** |

**濃縮率で見ること。** 生のシェアは「単にバンドを少なく置いた版」を有利に
見せる。x1.00 が「空が場所を気にしていない」状態、着手前は
**砂漠が惑星で一番雲の多い地面だった**。

**季節はケッペンの2文字目を運んでいる。** 夏雨型の陸地の上の雲は、
1月→7月で北半球 +27%・南半球 −55%。海上は no-data 項なので振らない
（つまり**全球平均では季節差はほぼ出ない。地域で測ること**）。

#### 途中で踏んだ分岐と、その計測

**降水量をそのまま雲量にすると極が空になる。** ケッペン表では**極冠は砂漠**
（氷床の年降水量はサヘルより少ない）。第1版はそれをそのまま雲に流したので、
**2600個の雪片が南極の完全な晴天の中を落ちていた**（雪地点の雲量 0.0011、
全球平均 0.055）。§2-6 の「快晴の空から雪が降る」を反対側から作り直した形。

**雲量はミリ数ではなく、空気が保持できる量に対するミリ数。**
冷たい空気はほとんど保持できないので、極の空は熱帯なら干ばつの総量で
曇る。降水量を「寒さで落ちる容量」で割ってから雲量として読む形に変えた。

**容量を赤道から滑らかに落とす（cos²緯度）と亜熱帯の閾値まで緩んで
サハラに雲が戻る。** 実測 x1.35 → **x1.55**。だから**緩和は38°より高緯度に
限定**してある。以下34°以下は従来どおり生の降水量を読む。

| 版 | 熱い砂漠の濃縮率 | 雪地点の雲量 |
|---|---|---|
| 着手前 | x1.82 | — |
| 降水量そのまま | **x0.92**（最良） | **0.0011**（極が空） |
| cos²容量 | x1.55 | 0.0165 |
| **採用（38°以上のみ緩和）** | **x1.35** | **0.0100** |

**2つの失敗はトレードオフの関係にある。** 砂漠の勝ち分を全部取ると
極が空になる。採用版は砂漠の改善を2/3残して雪の上に空を戻した位置。
**降水量そのままの版が砂漠指標では最良である事実は消えない** ——
極の雲を別系統（雲量そのものを気候から与える）で持てるなら再訪の価値がある。

#### 副産物のバグ（実バグ、修正済み）

`typhoonCentre` が**負の age を分数乗**していた。`typhoonAge` は
「今は台風がいない」を −1 で返すので、**サイクルの静穏側の全期間、
台風の256個のインスタンス行列が NaN だった。**
つまり**「台風と台風の間の静かな時間」は NaN 行列が何も描かないことで
偶然成立していた。** age をクランプし、不在時は `liveScale = 0` で明示的に
畳む形にした。

**未達**: **G36（雲の下でだけ降る）はこの構成では不可能**と計測で確定した。
雲影テクスチャで測ると、**全球の平均被覆率は 5.5%、雪地点では 1.0%**。

### 2-20. 雨（G34、完了）

**この作品で初めて雲から何かが落ちた。** §2-6 の「降雨は一行も存在しない」は
リストの中で最後まで生き残っていた項目だった。

**粒ではなく面（veil）。** この縮尺では雨粒は見えず、筋として描けば画面で

——雲底から下へ広がる細い繊維の束——なので、**セルごとに開いた円錐1個、
惑星全体でドローコール1本**にした。

**降るのは storm / typhoon のセルだけ、かつ降水場が「ここは雨」と言う場所だけ。**
判定は雲と同じく**流れ着いた先**で読む（`precipitationAtSeason`）ので、
**サハラへ入る雷雲は帳を閉じた状態で入ってくる**。強度には `liveScale` を
掛けてあるので、消滅期の台風は「雨をやめる規則」ではなく
**綿が無くなったから降らない**。§3 が要求している因果の向き。

| | |
|---|---|
| 帳の総数 | 221（storm系ノジュールの5個に1個） |
| 同時に降っている数 | 平均 49.1（最小 30・最大 150） |
| 降っている帳の下の平均降水量 | **0.677**（惑星平均 0.393） |
| **乾燥地の上で降っていたフレーム数** | **0 / 3489** |

**ドローコール +1**（155 → 156）、三角形 +1,596。
（なお §2-19 で雲の蒔き方が変わり嵐バンドの本数が動いたため、
シーン全体は §2-17 時点の 147 から 155 に増えている。）

#### 見えない雨をデバッグで見つけた話

最初の版は**セルの真下**に垂らした。球を外から見ると、**リム以外のあらゆる
方向で雲が自分の雨の手前に来る**ので、**帳は正しく描かれているのに
どこからも見えなかった**。マゼンタ単色に差し替えて初めて、
雲の縁からわずかに覗いていることが分かった。

**風下へずらして解決した。** セルの grain 方向に `size * 1.15` 逃がし、
軸も 0.4 だけ風下へ倒し、裾を雲より広く（底半径 = size * 1.25）した。

**未達**: それでも**真上から見たセルの雨は自分の雲の裏**にある。これは球を
外から見ることの幾何であって、嘘をつかない限り直らない。リム付近と、
帳が雲から外れて垂れている側で読める。

### 2-21. 稲妻の「形」は作って捨てた（G40、計測して不採用）

**実装して、計測して、消した節。** 差分は残っていないので、同じことを
やり直さないためにここに理由だけ書く。

作ったもの：曲げた針金のような折れ線（6セグメント、セルの底から地表まで、
節ごとに横へ振れる）を追加インスタンスメッシュ1本＝**ドローコール+1**で。
発光は既存のフラッシュ（`stormBands` の emissive スパイク）に同期させ、
**落雷点は雨の帳が毎フレーム出している `rainStrength` から選ぶ**ので、
「降っているセルからしか落ちない」は無料で手に入った。実測：
稲妻が画面に出ているのは全フレームの 6.51%、その下の平均降水量 0.645
（惑星平均 0.393）、**乾燥地の上での落雷 0本**。因果は完全に正しかった。

**それでも見えなかった。** 理由は幾何で、調整では動かない:

- **雲底の高度は `hover` = 0.14〜0.34、球の半径は 2.0。** つまり稲妻の
  実長は画面上で **15〜35px**。このカメラでは球面1ユニットが約108px。
- 太さを実寸で置くと **0.3px**（＝描かれていないのと見分けがつかない）。
  3px まで太らせると今度は**セルの綿の上に乗る**。綿は白く飽和しているので、
  **白い稲妻も加算合成の光も、そこでは一切見えない。**
- 風下へ逃がす（雨の帳と同じ手）を 2.0×size まで試したが、
  **セル自体が多数のノジュールの塊なので、綿の外へ出すには
  「嵐から離れた所に落ちる」まで動かすことになる。**

**唯一の逃げ道は「雲デッキの高さより何倍も背の高い稲妻を描く」ことで、
これは縮尺について嘘をつくことになる。** この作品はやらない。
フラッシュ（セルが内側から光る）は残っている。

**再訪する条件**: カメラがもっと寄れるようになるか、雲デッキの高度が
上がるか、嵐セルが海の上だけで光ると割り切れるようになったとき。
**「見えない実装が入っている」状態にはしない**（デバッグ用マゼンタで
「描画はできている」ことは確認済み。問題は描画の有無ではない）。

### 2-22. 雨に濡れた地面と海（G39、完了）

雨（§2-20）が入ったので、**降った跡**が初めて意味を持つようになった。
追加のドローコールもテクスチャも**ゼロ**：雲影マップ（512×256、既に
毎フレーム引かれている）の**青チャンネルが空いていた**ので、そこへ
「降っているセル」だけをもう一度スタンプしている。
R = 雲があるか、G = その緯度の移流速度、**B = そこに雨が降っているか**。

**引く位置は少し風上にずらしてある**（`sign(omega) * 0.022`）。真下は
雲影が仕事をしているので、**濡れた跡がセルの後ろに尾を引く**方が
「たった今降られた地面」に見える。

**陸と海で出す変化が違う。これが計測ではなく判断の部分。**

- **陸**: 塗装の明度を 20% 落とすだけ（**乗算**。linear 空間で引くと
  キーラインが出る、§2-15）。**光沢は足していない** ——
  「岩だけがマット」は既存の明示的判断（§2-18）。
  ただし**陸の効果は §2-16 の罠で半分見えない**（植生が地面を覆っている）。
- **海**: こちらが本命。**雨は水面を荒らす**ので、`roughness` を 0.3 → 0.78、
  さらに**クリアコートの粗さ 0.16 → 0.55**（この海の艶はほぼ全部
  クリアコート側にあるので、ベースだけ荒らしても数字が変わって絵が変わらない）。
  **降っている間だけ艶が消える**。海が「唯一光る物」であることは変わらない。

**計測**（惑星一周、陸上198,431点）:

| | |
|---|---|
| 濡れて見える陸の割合 | 1.01%（同時に） |
| 濡れている所の平均降水量 | **0.688** |
| それ以外の陸の平均降水量 | 0.368 |
| コスト | **ドローコール 0本、テクスチャ0枚**（既存の空きチャンネル） |

**見えることの確認方法**: 効果が微妙なので、**海の diffuse をマゼンタに
差し替えて「どこに出ているか」を先に撮った**（60px級の斑が2つ、
嵐の風上側の海に出ていた）。位置と大きさを確認してから本番の値に戻している。
§2-21 の教訓（「描かれていない」と「見えない」は画面上で同じ）の実践。

### 2-13. 砂丘がアーモンドに見えていた（第2弾で修正）

`dune` のモデルが球を (1.5, 0.18, 0.55) に潰した楕円体だった。この潰し方は
上から見て両端が尖ったレンズになり、しかもその尖端が空中で終わる。描画サイズ
では1個1個が**アーモンド**に見え、砂に見えなかった。加えて配置ループが全
インスタンスにローカル上向き軸まわりのランダムスピンを与えており、**エルグの
中で稜線が一本ごとに別方向**を向いていた。

裏面を平らにし（見えるのは地上部だけなのに下半球を抱えていたことが、そもそも
全体を薄くせざるを得なかった原因）、風下側を圧縮して滑落面を作り、両端を砂へ
沈めた。向きは `duneBearing`（超低周波の場）から取り、隣接する砂丘が揃う。

## 3. 構造的な問題

> **気象の「発生源」が一元化されていない。**

雲は雲用ノイズ、雪は緯度、雷は雲タイプ、乾燥度はケッペン、川は標高 —
5つが全部バラバラの根拠で動いている。だから「快晴なのに雪が降る」「雨は
降らないのに川がある」「雲が気候と無関係な場所に湧く」が同時に起きる。

あるべき姿は1つの気象場から全部を派生させること。
**これは `docs/design-memo.md` の当初の依存関係（層3 空＝雲・降水量 →
層4 バイオーム）そのもので、実装が途中で逸脱した形。** 復元にあたる。

```
ケッペン区分 ─┬→ 降水量プロキシ ─┬→ 雲量（どこに雲を置くか）
             │                  ├→ 雨（雲の下、暖候）
             │                  ├→ 雪（雲の下、寒候）
             │                  ├→ 雷（対流性の強い所だけ）
             │                  └→ 川の流量の重み
             ├→ 乾燥度 → 塗装・植生（実装済み）
             └→ 林冠密度 → 森林（実装済み）
```

降水量プロキシは**データがもう手元にあるので実装コストが小さい**のに、
雨・雪・雲・雷・川の5系統を同時に正す土台になる。費用対効果が最大。

## 6. 作業のやり方（踏襲すること）

- 検証は毎回 `npx tsc --noEmit && npm run build`
- ローカル確認は `(nohup npx vite preview --port 4173 --host > ログ 2>&1 &)` を
  **専用のBash呼び出しで単独実行**（pkillと同じコマンド内で起動すると
  レースコンディションで落ちる）
- ヘッドレス検証は Playwright（`/opt/pw-browsers/chromium`、
  `/opt/node22/lib/node_modules/playwright/index.js` は CommonJS なので
  `import pkg from ...; const {chromium} = pkg;`）。swiftshaderのため
  ビルド完了まで50〜70秒かかるが正常
- git: featureブランチにpush → `git fetch origin main && git merge-base
  --is-ancestor origin/main HEAD` で確認 → mainへfast-forward push
  （**mainへのpushでのみ自動デプロイが走る**）→ Actions の conclusion=success を確認

### 計測フック（推測で判断しないための道具）

いずれも**一時的に仕込み、コミット前に必ず戻す**。

1. **植生センサス** — `species.ts` のメッシュ構築直前に
   `if (location.search.includes('debugveg')) window.__veg = {placements,
   forestPoints, grassPoints, points, screePoints}` を仕込み、
   Playwrightの `page.evaluate` で地域ごとに集計する。
   緯度経度への逆変換は **`lon = atan2(z, -x) * 180/π - 180`**
   （`-180` を忘れると地球の裏側を測ることになる。一度やらかした）
3. **フィールドプローブ** — `window.__probe = (x,y,z) => sampleAt(dir)` を
   同じ場所に仕込み、地域ごとに lat/lon 格子で叩く。「植生が置かれない」
   のが**どのフィールドのせいか**を切り分けられる。第1弾で本命の原因
   （中間レリーフノイズと海面グレー閾値）はこれでしか見つからなかった。
   緯度経度 → 方向ベクトルは
   `x = -sin(θ)cos(φ), y = cos(θ), z = sin(θ)sin(φ)`
   （`θ=(90-lat)·π/180`, `φ=(lon+180)·π/180`）
4. **ラスタの直読み** — `public/world-elevation.png` をブラウザの canvas に
   描いて `getImageData` し、既知の地域のヒストグラムを取る。
   **定数が本当にデータと合っているかは、これでしか分からない。**
   ELEVATION_SEA_GRAY が2つずれていたのはこれで判明した
2. **平面展開図** — `buildTerrainTexture` の `ctx.putImageData` 直後に
   `if (location.search.includes('debugcanvas')) window.__terrainCanvas = canvas`
   を仕込み、`canvas.toDataURL()` で抜く。3D投影より地理的正しさの判定が確実

## 9. 判断の記録（蒸し返さないために）

- **雲・飛行機・衛星に真鍮線の支持棒を立てる案**（外部レビューで「効果大・
  コスト小」と評価された）は**不採用**。この作品は浮遊感を一貫して排除して
  きた経緯があり、人工物を足す方向は逆行する。
- 外部レビューのうち、ライティングのデスクランプ化・雲シェーダの全面刷新も
  現時点では**不採用**。
- 大気シェル（白い薄膜）は過去に意図的に削除済み。復活させないこと。
- **周辺環境は「重厚な書斎」。明るくモダンな書斎を試して却下した。**
  シーンは暖色キーライト1灯＋極小のアンビエントで、これが球の「撮影された
  実物」感を作っている。淡い壁が自前の拡散昼光を持つと、硬い暖色ランプで
  照らされた被写体の背後に別光源の面が来ることになり、**2枚の写真を合成した
  ように見える。** 同じ1灯でフレーム全体を説明できるのは濃い胡桃材と低照度。
- **背景の壁は写真1枚（`public/study-wall.jpg`、Gemini生成）。** ジオメトリで
  作らない。被写界深度の外なので鮮明に見えることがなく、幾何を作るのは無駄。
  ただし**プレーンのサイズは「見える範囲」に合わせること** — 幅80で貼ると
  13ユニット奥・画角40°では画像の中央23%しか映らず、書棚が全部画面外に出る。
- **子午線環（球を囲む真鍮の半円弧＋目盛り）は削除済み。復活させないこと。**
  「地球儀の視覚文法」として一度は追加したが、この作品のフレーミングでは
  カメラ正面の平面に置かれた環はシルエット上の円に射影される。つまり真鍮が
  リムをぐるりとなぞり、球が「机に置かれた物」ではなく「枠の中に嵌った物」に
  見える。台座の襟（collar）だけで「支えられている」ことは十分伝わる。
- シャドウマップは実機クラッシュの原因として無効化した経緯がある（G26で
  復活を検討する際は、実機での安全域を見極めながら）。
