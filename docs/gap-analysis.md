## 0. プロジェクトの定義（あるべき姿）

> **工房の作業台に置かれた、手作りの地球儀ミニチュア。
> 見た瞬間に「どこ」か分かり、しばらく眺めると「生きている」と分かる。**

4つの柱に分解する。

1. **物としての説得力** — 樹脂の海、塗装した陸、綿の雲、植毛の緑、真鍮の金具。
   宇宙に浮かぶ惑星のCGではなく、机の上に実在する物体として撮影された絵。
2. **一目で「どこ」か分かる** — 地形・気候・植生・建造物が実座標。ただし
   **地理の教科書ではなく土産物の地球儀**。正確さではなく「その地域といえば
   コレ」という記号の強調がゴール。アマゾン＝密林と大河、サバンナ＝アカシアの傘、
   地中海＝糸杉、北欧＝トウヒ、砂漠＝砂丘。
3. **生きている** — 四季（1分＝1年）、風と雲、昼夜と街の灯り、船・飛行機、
   噴火、台風。
4. **携帯で動く** — 単一品質構成、シャドウマップ無効、ドローコール抑制。

### 2-1. 森林密度（立体角あたり、惑星全体を実測）

| **コンゴ盆地** | **0** | **10,207** | チベット | 315 | 159 |
| **ボルネオ** | **678** | **11,054** | シベリア中央 | 88 | 8,008 |

### 2-2. 原因1：森林判定が気候ではなく標高で決まっていた（解決済み）

`species.ts` の森林条件にあった `height >= SEA_LEVEL + 0.02` が、
気候的に適地である陸地候補の**75%を単独で落としていた**。
旧・架空地形時代（陸＝丘）の名残。実標高データでは陸の大半が平坦な低地。

**撤廃済み。** 陸地レイヤの標高ゲートは全廃し、判定は「海面より上か」だけ。
海岸の砂浜帯（`COAST_WIDTH` = 0.006）を避ける程度の余裕すら広すぎる
——コンゴ盆地の平均海抜がちょうど 0.007 だから。

### 2-3. 原因2：badlands がノイズのままだった（解決済み）

陸地候補の 19.4% が `badlandsAt`（純粋なfbmノイズ、地理情報ゼロ）で
植生を拒否されていた。**ケッペンB群・Ds群駆動に変更済み**
（`KOPPEN_BADLANDS`）。メサはコロラド高原とゴビに立ち、サハラは砂丘になった。

### 2-4. 原因3：絶対数が足りなかった（解決済み）

惑星全体で2,700個弱。**31,627個に増やし、1個あたりを小さくした。**
森林の最小間隔は林冠密度で可変（熱帯雨林 0.0065／疎林 0.017）。

### 2-4b. 途中で見つかった上流のバグ2件（いずれも解決済み）

G1に着手して初めて分かったが、**「そこが陸かどうか」を決めていたのは
標高ゲートだけではなかった。**

1. **符号付き中間レリーフノイズが平地を海に沈めていた。**
   `heightAt` の `midRelief * 0.145 * landMask` は振幅±0.021。海抜が
   数千分の一しかない盆地では自分の海抜の数倍あり、下向き半分が
   そこを水没させていた。**標高ラスタ上では100%陸地のコンゴが57%水没、
   サヘル62%、シベリア中央66%。** landMask の下端を `SEA_LEVEL - 0.03`
   から `SEA_LEVEL` に上げて解決。

2. **陸/海のグレースケール閾値 145 が最下位の陸地帯を切っていた。**
   ラスタを直接測ると、既知の浅海（北海）は最大143、既知の平坦な内陸
   （コンゴ盆地・グレートプレーンズ）は147から始まる。**144〜145 が
   世界で最も平坦な低地の値** —— アマゾン盆地の60%、パンパの73%、
   西シベリア平原の83%がここにいて、全部が海として読まれていた。
   **143に変更。** 面積加重の陸地比率は 23.8% → **28.0%**（地球の実際は約29%）。
   あわせて陸の第一段を砂浜帯より上に持ち上げた（`ELEVATION_LAND_FLOOR`）。
   でないと「非常に低いだけの大陸」が丸ごと砂浜色に塗られる。

### 2-4c. 熱帯雨林が茶色く塗られていた（解決済み）

`biomeColor` のラテライト（`tropicalSoilColor`）が `tropical`（＝実質的に
緯度のみ）でゲートされており、**降水量と正確に反比例して赤土を塗っていた。**
林冠が閉じている赤道直下で最大強度0.65、20°南のセラードでゼロ。
アマゾンとコンゴが泥色で隣のサバンナが緑という逆転。乾燥度でも
ゲートして解決（セラードとサヘルの見た目は不変）。

### 2-5. 海の波

- 波は**静止バンプテクスチャの横スクロール** = 模様全体が自転軸まわりに剛体回転。
- 頂点変位の振幅は最大 **0.0019**（半径2の球に対し1/1000）。
- 波長0.45に対し海メッシュは76×44（赤道で1辺0.165）＝**1波長2.7頂点**で破綻。
- ~~**海岸の白波が存在しない。**~~ → 第2弾で実装（§2-10）。

### 2-6. 降水

- **降雨は一行も存在しない。** 嵐雲は雷を光らせるが何も降らない。
- 降雪は緯度のみで判定。海陸を区別せず、気候区分を見ず、**雲と無関係**
  （快晴の空から降る）。雪片は固定方向なので**同じ場所が永遠に降雪地点**。
  塗装の雪線とは完全に独立した2系統で、積もらない。
- ケッペン区分は降水パターンの分類（f/w/s/m）そのものなのに、**降水量として
  使っていない**。

### 2-8. 川がほぼ動いていない（第1弾中に計測で判明 → **§2-39 で解決**）

`biomeColor` を全項目分解して計測した副産物。

- 流量累積の**全球最大値が242**。`strength = (ln(flow+1) - 3.4) / 2.5` は
  青くなるのに flow > 29、最大強度に flow > 364 を要求するので、
  **惑星上のどのセルも最大強度に届かない。** 何らかの川が見える陸地セルは0.68%。
- 原因は D8 の落とし口探索が `<` の厳密比較で窪地埋めがないこと。
  **陸地セルの12.6%がシンク**になり、平地で流れが止まって本流が育たない。
- アマゾン箱の最大流量22、コンゴ箱33。**どちらにも川のピクセルが1つもない。**

**関連する時限爆弾**: `deltaCoast = 1 - smoothstep(elevation, 0, 0.05)` は
アマゾンで0.907、コンゴで0.845。いま `riverStrength` が0だから何も起きて
いないだけで、水系を直した瞬間に堆積扇の砂色 `#a99568` が最大0.50の割合で
**盆地全体を3,000km内陸まで塗る。** 直すときは `deltaCoast` を
terracedElevation ではなく生の海抜（例 `smoothstep(h, SEA_LEVEL, SEA_LEVEL+0.008)`）
で取ること。G27に着手する人へ。

### 2-10. 白波は「深さ」ではなく「岸からの距離」（第2弾）

最初の実装方針（`SEA_LEVEL` より浅い水深でゲートする）は**間違い**だった。
大陸棚は幅全体が浅いので、深度0.013の帯で**北海・アイリッシュ海・スンダ棚・
タイランド湾がまるごと白くなった。** 平面展開図に出すまで気づけない類の失敗。

正しい量は**海岸線からの距離**。陸マスクに対する2パスのチャンファー距離変換
（1 / √2、経度の継ぎ目で巻く）で距離場を作り、そこから帯を描く。
幅と強度は `coastCliffiness` と沿岸方向の中周波fbmで変え、`coastlineJitter`
をテクセル単位で加えて塗装された海岸線と一緒に揺らす。

実測（2048幅）: 白波ピクセルは全球の1.15%、東南アジア12.6%、地中海10.6%、
英国6.7%、太平洋中央0.60%（島のみ）、大西洋中央0.00%、サハラ0.00%。

### 2-11. 都市（第2弾）

28都市 → **186都市＋17の都市回廊**（`URBAN_FEATURES`）。回廊は東海道・山陽・
米北東部・ライン=ルール・ロンドン=マンチェスター・ガンジス・ナイル・長江
デルタ・珠江・インダス・ジャワ北岸・サンパウロ=リオ等。

**`urbanAt(dir)` が単一の真実。** 昼の灰色塗装・夜の灯り・植生の伐採が全部
これを読む。2系統が別式で「都市はどこか」を計算するのは §2-6 の雪線／雪片の
分裂と同じ失敗になるため。

- 市街地面積は陸地の1.27% → **2.40%**（球の0.74%）。モンテカルロ30万点。
  パッチ半径を `0.014 + size*0.026` → `0.0085 + size*0.0135` に縮めて調整。
- **性能は7倍の要素数で逆に速くなった**: 900k回の `urbanAt` が117ms → **68ms**。
  5°×5°のバケットグリッドをモジュール読込時に1回作る。
  ページ読込時間は同一ビルドで79秒と115秒に振れて使い物にならないので、
  関数を直接ベンチした。
- 植生の伐採は`urbanAt`の生値では足りない。塗装用に調整された値をそのまま
  使うと**核でわずか27%の間引き**にしかならず、灰色の上に木が立ったままだった。
  2.6倍して核を飽和させ、28都市で計測: 中心0.012rad以内 **-80.0%**、
  0.012–0.022radの環 -30.1%、0.06rad超 -0.2%、惑星全体の森林 -0.4%、
  草は -37.5%（公園として残す）。
  **計測は都市サイズの帯で行うこと** — パッチは東京でも約0.018radしかなく、
  0.03radの傘で平均すると効果が消える。

**標高ラスタは世界の大デルタを海として読む。** 回廊の候補を直接プローブした
結果: 上海=南京は21点中14点、上海=杭州18/21、カイロ=アレクサンドリア15/21、
ルール=ランドスタット14/21が `SEA_LEVEL` 未満。初稿14本のうち4本は昼に何も
塗らず夜に外洋を光らせるところだった。**経路はアトラスではなくラスタに対して
引くこと。** 同様に**186都市のうち26都市の中心座標が水ピクセル**
（ニューヨーク、ムンバイ、上海、ラゴス、ヒューストン、バルセロナ、
コペンハーゲン等）。今はパッチが隣接する陸を覆うので無害だが、
**G43/G48で建物や港を都市の正確な座標に置くと海の中に建つ。**

**`habitabilityAt` は強く熱帯寄り（未着手）。** 平面展開の夜図では
アマゾン・コンゴ・島嶼部東南アジアが欧州や米東部より明るく光る。
誰もが知る夜の地球の画像の**正反対**。都市テーブルではなく散在灯りのパスの
問題で、G47の次の実体。

### 2-12. 明暗境界は動かない（第2弾で判明）

**キーライトもカメラも固定なので、明暗境界は円盤上を掃かない。** 太陽は
カメラ軸から約55°離れており、境界は**円盤半径の約58%、反太陽側**に固定される。
地形がその線を通過していくのであって、線が地形の上を動くのではない。
夕暮れを検証する人は**左リム（＝太陽側で最も明るい）ではなくこちらを見ること。**

初版の夕暮れ帯が不可視だった原因は2つ、どちらも同じ間違い方をしていた。

1. `diffuseColor.rgb` を掛けると効果がアルベドに比例し、**境界が最も長く
   横切る面である暗い海の上でほぼゼロ**になる。
2. ドット積で幅0.08の窓は円弧にして約4°、このフレーミングで約20ピクセル。
   露出1.9のトーンマッピングで潰れる。

幅と強度を上げ、暗い海にも乗る下限を入れた。ただし**海の暖色帯は陸より
大幅に弱くしてある** — 暗い青に橙を足すと夕焼けではなく**茶色い汚れ**に
見えるため。海側はブルーアワー（寒色帯）に役割を持たせている。

**検証手法の注意**: 回転停止トグルで位相を揃えたA/B比較を試みたが、
**季節アニメーション（1分＝1年）が止まらない**ため2回のキャプチャで
北米の紅葉が別フェーズになり、85%の画素が変化して判定不能になった。
季節を止める手段が現状ない。画像A/Bをやるなら先にそこを用意すること。

### 2-14. シャドウマップ無しで雲影を落とす（レビュー第1位への対応）

**この作品には影が1つも存在しなかった。** `main.ts` で
`renderer.shadowMap.enabled = false`（実機クラッシュの犯人として切り分け済み、
復活させないこと）なのに、キーライトと球・海・台座・小物すべてに
`castShadow`/`receiveShadow` が立っていて**全部無効**だった。木は地面に、
雲は海に、陸は海面シェルに、球は机に、どれも影を落とさない。
外部レビュー（Gemini）も独立に同じ場所を指摘した。

雲影だけはシャドウマップ無しで落とせる。**雲が閉形式で動くから**である：
ノジュールの経度は `lon + zonalOmega(lat) * t` でしかなく、雲グループは
globeGroup の子なので、球の物体空間ではこれが運動の全て。デッキを一度
equirectangular に焼き、シェーダ側で**同じ式で引く位置をずらす**だけで
影が本物の雲に追従する。レンダーターゲット無し、追加パス無し、
テクスチャフェッチ1回。

- 実装は `buildCloudShadowTexture`（512×256 RGBA）。**R = 被覆、
  G = その緯度の移流速度**。G を使うのは、風プロファイルをGLSLに
  書き写すと噴煙で一度潰した「2つの式」問題の再発になるため。
  omega は緯度のみの関数なので行定数チャンネルで厳密に運べる。
- 強度は陸0.38・海0.62。**海を強くするのは意図的** — 外洋は自前の
  テクスチャをほとんど持たないので、横切る雲影が「空の下の面である」
  ことを語る主役になる。0.42では素の海色が暗く相対差が出ず、ほぼ
  見えなかった。
- **既知の近似2つ**: (1) 影は雲の真下に落とす（光源方向のオフセット無し）。
  (2) 帯の蛇行 `meanderAmplitude` を無視。最大0.085 rad（約4.9°）だが
  熱帯（20°未満）と極（75°超）ではゼロなので、このフレーミングで海が
  最も見える領域では誤差ゼロ。台風のノジュールは自分の移動フレームに
  いるため除外（閉形式が当てはまらない）。

### 2-15. 残りの影2種（完了）

**海岸の接地陰は「書いてあるが効いていない」状態だった。** 計測値：陸地全体の
平均 |AO| は **0.0040**（最大 0.16 の 2.5%）、|AO|≥0.02 は陸の 3.61% だけ。
しかも**外し方が両方向に同時に間違っていた**：

- 海岸線から3テクセル以内の陸（陸の 10.2%、80,227テクセル。この効果が存在する
  理由そのものの帯）のうち、**|AO|≥0.08 を受けていたのは 16.5% だけ**。
  崖の海岸は1テクセルで海抜0.006を超えるので、**最も影が要る場所で影が付かない**。
- 逆に、darkening を受けたテクセルの **12.9% は海岸から8テクセル以上内陸**。
  平坦な内陸は数千kmにわたって海抜0.006未満だから（コンゴ盆地の平均は0.007）。

**原因は §2-10 の白波と完全に同じ。正しい量は海岸線からの距離であって、
標高ではその距離を表現できない。**（デルタは内陸まで低く、岬は水際で高い。）
既存のチャンファー距離場に `side: 'sea' | 'land'` を足して陸側でも引けるようにし、
そこから帯を描いた。結果：**海岸帯の被覆 16.5% → 100.0%、内陸への漏れ 12.9% → 0.0%。**
幅と深さは `coastCliffiness`（実際の `coastalStep` を駆動しているのと同じ場）と
白波と同じ沿岸方向ノイズで変える。海側にも同じ理屈の遮蔽（`shoreOcclusion`）を
白波の**下に**敷いた。泡は明るいまま暗い襟の上に乗るので白のコントラストが上がる。

**方向を持たせないのは意図。** 球は固定キーライトの中で自転するので、光源方向を
焼き込んだものは回転の大半で嘘になる。海岸の隅の水は太陽がどこにあろうと空を
見込む量が減るので、方向なしの遮蔽が安い答えであると同時に正しい答え。

#### ここで踏んだ罠2つ（どちらも平面展開図でしか見つからない）

1. **`offsetHSL` は linear 空間で定数を引く。** THREE.Color は linear なので、
   linear 輝度 0.15 しかない海岸の緑から 0.24 を引くと**暗くなるのではなく黒に
   クランプする**。全大陸が**硬い黒の輪郭線**を身に着けて出てきた —— この作品が
   一貫して避けてきたデカール読みを、事故で自分から作った。
   **遮蔽は届く光を「掛ける」もので、定数を引くものではない。**
   乗算なら暗いテクセルも明るいテクセルも同じ「割合」を失うので、
   原理的にキーラインが出ない。以後この3項目は全部乗算。
2. **強い darkening を気候ラスタに直結すると、最近傍の階段エッジ（§2-9）が
   フルコントラストで描かれる。** 東南アジアが矩形の集合になった。
   **強度を下げても矩形が薄くなるだけで直らない。**
   引く「方向」を細かいノイズでワープさせること（`canopyWarp`）。境界が
   グリッド数セル分ゆらいで階段でなくなり、本当に鋭い所は鋭いまま残る。

### 2-16. 林冠の接地陰は塗装だけでは半分（完了）

`canopyAt` で塗装を暗くしただけでは足りない。**3Dで見て初めて分かったが、
31,600個のインスタンスが地面をほぼ完全に隠しているので、塗装だけ暗くしても
「木と木の間」が変わるだけで木自体は何も変わらない。**

クランプ側にも同じ陰を入れた。既存の per-clump の明度ばらつきは `rand()` 由来、
つまり**白色ノイズ**で、隣同士を無相関に振るので「平らな塊の上のスペックル」に
しか見えない。森の明暗は逆に強く**構造化**されている：閉じた林分の底は隣が
屋根になるので暗い、同じ林分の縁は各樹冠が空を見るので明るい、屋根の上に
突き出た emergent が最も明るい。

3項（すべてインスタンス色に載るだけでジオメトリもマテリアルもドローコールも増えない）:
`canopyAt`（林冠の閉じ具合、間隔を決めているのと同じ場）×
サイズ階層由来の「埋もれ具合」（小さいクランプが林床、大きいものは光を保つ）×
**空間的に連続な**パッチノイズ（これが影とスペックルの違いそのもの。周波数は
クランプではなく林分のスケール）。

計測（塗装側）：閉じた林冠の地域が **6〜11% 暗く**（コンゴ -10.9%、米東部 -10.0%、
アマゾン -8.3%）、砂漠と高原は **0.1% 以内で不変**（サハラ 0.0%、豪州内陸 -0.0%、
チベット -0.1%）。海側の変化は面積の 2.4%、平均 -0.0007。

### 2-18. 構図・鏡面・机への影（完了）

84% → 63%。既に作ってあった本の山や鉢植えがようやく機能するサイズになる。

### 2-17. 雲の質感（G8、完了）

**「同じ丸い塊」も計測できる。** 着手前：ノジュール830個、サイズの
90/10パーセンタイル比 **2.58**、そして**惑星上の全ノジュールの 63% が中央値の
±30% 以内**。1つの粒径は1つの材質に見え、同じ大きさの球でできた材質は
綿ではなく発泡スチロール。

ちぎった綿は逆の統計を持つ —— 少数の大きな塊、それに寄りかかる肩、縁から
むしれた大量の粒。クラスタ内でノジュールに順位を付け（後のものほど小さく
背骨から離れる）、**局所の bulk でスケールされない**ほぼ固定サイズの房を
その外側に置いた。端では房を最後のステップより先に投げ、塊自体を落とし始めるので、
帯は「一回り小さい球」で終わらずに**ちぎれた粒に解ける**。
比 2.58 → **3.32**、±30%内 63% → **55%**（帯タイプ単体では 32〜44%）。

**引き伸ばしと櫛通しはビルド時に焼けない。ここが一番おもしろい所。**
従来の回転は法線への**最小回転**でノジュールを立てており、これは位置依存の
ねじれを持つ。だからビルド時に固定した向きは、風が帯を運ぶにつれて狂っていく
——偏西風は1分で経度1ラジアン以上動かすので、**見ている間に櫛通しがランダム
スピンへ戻る**。方位角（コンパスベアリング）はこの移流に対して不変なので、
grain を毎フレーム解決する方式にした。grain・法線・従法線からインスタンス基底を
直接書き出すので、**置き換え前より per-frame が安い**（軸角構築なし、
クォータニオン積なし、TRS compose なし）。

**コストは renderer.info で実測した（推測ではなく）**：シーン全体の
ドローコール **150 → 147**（雲の予算は3本「減った」。ノジュール変種を帯単位
ではなくノジュール単位で交互配置したら最初は+2になり、変種を1つ削って払った）。
三角形 2,605,733 → 2,649,631（**+1.7%**）。レンダーターゲット・追加パスなし、
シャドウマップ不変、**チューニング済みのハロー／フリンジと灰色の輪の対策には
一切触っていない**。

**正直に未達**: ズームすると塊は「毛羽立った綿」ではなく「滑らかな白い小石」に
見える。ここから先はセグメントを増やすか、ハロー方式を開け直すかで、
どちらも当てずっぽうでやる価値はない。

### 2-19. 雲を降水場に繋いだ（第3弾の一歩目、G7）

**§3 の「気象の発生源が一元化されていない」に初めて手を付けた節。**
`precipitationAt` は完成していたのに消費側がゼロだった。雲はその5系統のうち
一番声が大きい —— 空はケッペンを一度も読んでいなかったので、**サハラの上にも
コンゴの上にも同じ確率で雲塊が乗っていた**。

**繋ぎ方は2段。雲は動くので、「どこで雨が降るか」の2軸は別物として扱う。**

- **緯度は帯状風に対して不変。** だから「その緯度にそもそも雲が何個あるか」と
  「何型か」は、新設した `zonalPrecipitationAt`（降水場の緯度平均）に対する
  棄却で決める。
- **経度は不変ではない。** だからローカルな側は**毎フレーム、流れ着いた先で**
  読む。**帯単位ではなくノジュール単位**なので、サヘルを横切る帯は
  モンスーン側が綿のままサハラ側だけがほつれる。
  ビルド時に焼いていたら §2-17 の「焼いた向きは移流で狂う」の再演だった。

**計測（16 RNG シード × 惑星一周ぶんの時間で平均）。**
帯は10本しかないので、**どの10箇所に当たったかが規則の差より大きく効く** ——
最初に1シードで比較したときは「砂漠好きが4倍になった」と出て、同じコードが
別シードでは逆を出した。**シード1本での前後比較はこの系では意味がない。**

| 指標 | 着手前 | 完了後 |
|---|---|---|
| 陸上の雲の下の平均降水量 | 0.364 | 0.446 |
| 乾燥地の上にある陸雲の割合 | 34.8% | 24.6% |
| **熱い砂漠の雲の濃縮率**（単位面積あたり／全球平均） | **x1.82** | **x1.35** |
| 夏雨型の陸地の上の雲量（北半球）1月→7月 | — | **+27%** |
| 同（南半球）1月→7月 | — | **−55%** |

**濃縮率で見ること。** 生のシェアは「単にバンドを少なく置いた版」を有利に
見せる。x1.00 が「空が場所を気にしていない」状態、着手前は
**砂漠が惑星で一番雲の多い地面だった**。

**季節はケッペンの2文字目を運んでいる。** 夏雨型の陸地の上の雲は、
1月→7月で北半球 +27%・南半球 −55%。海上は no-data 項なので振らない
（つまり**全球平均では季節差はほぼ出ない。地域で測ること**）。

#### 途中で踏んだ分岐と、その計測

**降水量をそのまま雲量にすると極が空になる。** ケッペン表では**極冠は砂漠**
（氷床の年降水量はサヘルより少ない）。第1版はそれをそのまま雲に流したので、
**2600個の雪片が南極の完全な晴天の中を落ちていた**（雪地点の雲量 0.0011、
全球平均 0.055）。§2-6 の「快晴の空から雪が降る」を反対側から作り直した形。

**雲量はミリ数ではなく、空気が保持できる量に対するミリ数。**
冷たい空気はほとんど保持できないので、極の空は熱帯なら干ばつの総量で
曇る。降水量を「寒さで落ちる容量」で割ってから雲量として読む形に変えた。

**容量を赤道から滑らかに落とす（cos²緯度）と亜熱帯の閾値まで緩んで
サハラに雲が戻る。** 実測 x1.35 → **x1.55**。だから**緩和は38°より高緯度に
限定**してある。以下34°以下は従来どおり生の降水量を読む。

| 版 | 熱い砂漠の濃縮率 | 雪地点の雲量 |
|---|---|---|
| 着手前 | x1.82 | — |
| 降水量そのまま | **x0.92**（最良） | **0.0011**（極が空） |
| cos²容量 | x1.55 | 0.0165 |
| **採用（38°以上のみ緩和）** | **x1.35** | **0.0100** |

**2つの失敗はトレードオフの関係にある。** 砂漠の勝ち分を全部取ると
極が空になる。採用版は砂漠の改善を2/3残して雪の上に空を戻した位置。
**降水量そのままの版が砂漠指標では最良である事実は消えない** ——
極の雲を別系統（雲量そのものを気候から与える）で持てるなら再訪の価値がある。

#### 副産物のバグ（実バグ、修正済み）

`typhoonCentre` が**負の age を分数乗**していた。`typhoonAge` は
「今は台風がいない」を −1 で返すので、**サイクルの静穏側の全期間、
台風の256個のインスタンス行列が NaN だった。**
つまり**「台風と台風の間の静かな時間」は NaN 行列が何も描かないことで
偶然成立していた。** age をクランプし、不在時は `liveScale = 0` で明示的に
畳む形にした。

**未達**: **G36（雲の下でだけ降る）はこの構成では不可能**と計測で確定した。
雲影テクスチャで測ると、**全球の平均被覆率は 5.5%、雪地点では 1.0%**。

### 2-20. 雨（G34、完了）

**この作品で初めて雲から何かが落ちた。** §2-6 の「降雨は一行も存在しない」は
リストの中で最後まで生き残っていた項目だった。

**粒ではなく面（veil）。** この縮尺では雨粒は見えず、筋として描けば画面で

——雲底から下へ広がる細い繊維の束——なので、**セルごとに開いた円錐1個、
惑星全体でドローコール1本**にした。

**降るのは storm / typhoon のセルだけ、かつ降水場が「ここは雨」と言う場所だけ。**
判定は雲と同じく**流れ着いた先**で読む（`precipitationAtSeason`）ので、
**サハラへ入る雷雲は帳を閉じた状態で入ってくる**。強度には `liveScale` を
掛けてあるので、消滅期の台風は「雨をやめる規則」ではなく
**綿が無くなったから降らない**。§3 が要求している因果の向き。

| | |
|---|---|
| 帳の総数 | 221（storm系ノジュールの5個に1個） |
| 同時に降っている数 | 平均 49.1（最小 30・最大 150） |
| 降っている帳の下の平均降水量 | **0.677**（惑星平均 0.393） |
| **乾燥地の上で降っていたフレーム数** | **0 / 3489** |

**ドローコール +1**（155 → 156）、三角形 +1,596。
（なお §2-19 で雲の蒔き方が変わり嵐バンドの本数が動いたため、
シーン全体は §2-17 時点の 147 から 155 に増えている。）

#### 見えない雨をデバッグで見つけた話

最初の版は**セルの真下**に垂らした。球を外から見ると、**リム以外のあらゆる
方向で雲が自分の雨の手前に来る**ので、**帳は正しく描かれているのに
どこからも見えなかった**。マゼンタ単色に差し替えて初めて、
雲の縁からわずかに覗いていることが分かった。

**風下へずらして解決した。** セルの grain 方向に `size * 1.15` 逃がし、
軸も 0.4 だけ風下へ倒し、裾を雲より広く（底半径 = size * 1.25）した。

**未達**: それでも**真上から見たセルの雨は自分の雲の裏**にある。これは球を
外から見ることの幾何であって、嘘をつかない限り直らない。リム付近と、
帳が雲から外れて垂れている側で読める。

### 2-21. 稲妻の「形」は作って捨てた（G40、計測して不採用）

**実装して、計測して、消した節。** 差分は残っていないので、同じことを
やり直さないためにここに理由だけ書く。

作ったもの：曲げた針金のような折れ線（6セグメント、セルの底から地表まで、
節ごとに横へ振れる）を追加インスタンスメッシュ1本＝**ドローコール+1**で。
発光は既存のフラッシュ（`stormBands` の emissive スパイク）に同期させ、
**落雷点は雨の帳が毎フレーム出している `rainStrength` から選ぶ**ので、
「降っているセルからしか落ちない」は無料で手に入った。実測：
稲妻が画面に出ているのは全フレームの 6.51%、その下の平均降水量 0.645
（惑星平均 0.393）、**乾燥地の上での落雷 0本**。因果は完全に正しかった。

**それでも見えなかった。** 理由は幾何で、調整では動かない:

- **雲底の高度は `hover` = 0.14〜0.34、球の半径は 2.0。** つまり稲妻の
  実長は画面上で **15〜35px**。このカメラでは球面1ユニットが約108px。
- 太さを実寸で置くと **0.3px**（＝描かれていないのと見分けがつかない）。
  3px まで太らせると今度は**セルの綿の上に乗る**。綿は白く飽和しているので、
  **白い稲妻も加算合成の光も、そこでは一切見えない。**
- 風下へ逃がす（雨の帳と同じ手）を 2.0×size まで試したが、
  **セル自体が多数のノジュールの塊なので、綿の外へ出すには
  「嵐から離れた所に落ちる」まで動かすことになる。**

**唯一の逃げ道は「雲デッキの高さより何倍も背の高い稲妻を描く」ことで、
これは縮尺について嘘をつくことになる。** この作品はやらない。
フラッシュ（セルが内側から光る）は残っている。

**再訪する条件**: カメラがもっと寄れるようになるか、雲デッキの高度が
上がるか、嵐セルが海の上だけで光ると割り切れるようになったとき。
**「見えない実装が入っている」状態にはしない**（デバッグ用マゼンタで
「描画はできている」ことは確認済み。問題は描画の有無ではない）。

### 2-22. 雨に濡れた地面と海（G39、完了）

### 2-23. 都市の大きさ・農地・砂丘の作り直し（レビュー指摘3件）

「都市のエリアが少ない／木が多すぎる箇所がある／砂漠がアーモンドに見える」
という3点の指摘に対する対応。**3件とも指摘が正しく、うち2件は
過去の『修正済み』が実は直っていなかった。**

#### (1) 都市が7pxだった

**画面上の大きさを測って初めて分かった。** 都市パッチ半径は186都市に
増やしたときに「総面積を維持する」ために縮めてあった（§7）。計算は正しいが
**目標が間違っていた**: 実測すると東京もカイロも**画面上7px**、
球全体が約500pxのなかの点。しかも上に木が生えているので何も見えない。

|---|---|---|
| 東京 | 12.7px | **17.2px** |
| サンパウロ | 10.8px | 16.7px |
| カイロ | 11.0px | 15.4px |
| ロンドン | 14.4px | 22.3px |

#### (2) 温帯大陸が海岸から海岸まで閉じた林冠だった

**これが「木が多すぎる」の本体。** ケッペンが「そこに生えうるもの」を
言っているだけで、**実際にそこにあるのは畑**。作物のラスタは無いが、
**「人が住んでいるか」の場は既にある**（`habitabilityAt` = 気候・標高・
都市リストのハロー。夜の街灯りが描かれている場そのもの）。木にも同じ場を
読ませた。**新しい場は作らない**（§3 の分裂を繰り返さないため）。

**間引きは確率ではなく「間隔」でやること。ここが計測でしか分からなかった点。**
最初は候補を確率で棄却した。ガンジス平野で**平均44%の間引きがかかっているのに、
木は2%しか減らなかった。** 閉じた林はパッキング律速なので、
候補を捨てても**次の候補が同じ場所に入るだけ**。Poisson-disc 層が聞くのは
距離だけ。間隔を `1/sqrt(1-farmed)` 倍にして解決。

**`SpatialHash` はこの変更で壊れかけた** — セルは「使う最大間隔」で作らないと
静かに近傍を取りこぼす（§7）。`FOREST_SPACING_MAX` を新設してある。

計測（0.12rad の円内の森林インスタンス）:

| 地域 | 前 | 後 | |
|---|---|---|---|
| アイオワ | 384 | **258** | −33% |
| ガンジス平野 | 135 | **91** | −33% |
| アマゾン | 594 | 598 | 0% |
| シベリア | 413 | 413 | 0% |
| コンゴ | 429 | 410 | −4% |

**間引くのは樹木だけ。** 岩（MINERAL）と低木は対象外 ——
畑はビュートを消さないし、生垣は残る。草も無傷（§2-11 と同じ理由で、
伐採跡が焼け野原に見えないため）。

#### (3) 砂丘はまだアーモンドだった（§2-13 の修正が不完全だった）

§2-13 で「高さを両端でテーパーした」が、**平面形は楕円のままだった**。
球を x に伸ばすと、ある x での断面半径が `sqrt(R²−x²)` で既に狭まっているので、
**y に何をしても上から見た輪郭はレンズ＝アーモンド。地球儀は上から見る。**

断面で正規化してから平面形を**明示的に**書き直した:

- 幅 `(1 - |t|^7)^0.4` — 端の1/5まで幅を保ってから丸く落ちる（＝尾根）
- 高さ `(1 - t²)^0.8` — 稜線が長く走り、両端で砂に沈む
- **断面は半円ではなく三角**（`(1-|nz|)^0.62`）。球の断面をそのまま使うと
  **ソーセージ**になる。砂は安息角で立つので稜線が出る
- 風下側 0.55 倍の圧縮（滑落面）と、長さ方向のわずかな蛇行

### 2-24. 海のうねりに法線が無かった（G14/G13/G17）

**「波が平ら」の原因は振幅でも解像度でもなく、法線だった。**

頂点シェーダのうねりは以前から入っていた。しかし**頂点を動かすだけで
法線を一切変えていなかった**ので、光は波の存在を知らない。法線を変えない
変位はシルエットにしか出ず、その振幅は 0.002 ユニット ——
このカメラでは**0.2px**。見えるはずがなかった。

**修正は解析的な勾配。** 波は object 空間の素の正弦波なので、
`A*sin(k·p + wt)` の勾配は `A*k*cos(k·p + wt)` で閉形式。
面に沿う成分だけで法線を倒せばよく、**cos 4回、差分もパスも増えない**。

**目で読んでいるのは高さではなく傾き `A*|k|`。** しかもこの面は
実際の海より遥かに敏感で、クリアコートが鋭く（roughness 0.16）海が球面で
一番暗いので、**ランプではなく部屋を映す角度になると真っ黒になる**。
最初4°で入れたら**両大洋に暗い斜めの縞（コーデュロイ）**が出た。半分の
約2°が「波ベクトルを主張しない」限界。

**波長はメッシュに対して決めること。** 従来は波数14と6を76分割の殻に
乗せていた（＝1波長あたり2〜3頂点。正弦波が幾何として存在できない）。
波数9・分割 **176×100**（G17も同時に解決。陸は384×216なので海岸のカクつきが
減る）で1波長あたり8〜9頂点。**これより細かいものはバンプマップの担当**
（そちらはテッセレーション律速ではない）。

**うねりは帯状風と一緒に流れる（G13）。** ただし**風のプロファイルを
GLSLに書き写さない**こと。`clouds.ts` が雲影マップの緑チャンネルに
緯度ごとの移流速度を焼いており、海のシェーダはその同じテクスチャを
既にバインドしている（影のため）。**テクスチャフェッチ1回で、空と海が
同じ貿易風・偏西風を読む。** サンプル点を `-omega*t` 回すのは波面全体を
その緯度線に沿って滑らせるのと同じで、赤道無風帯と亜熱帯高圧帯では
ちょうど停まる。

### 2-28. 空港と港（G45/G44、完了）

**どちらも自分の座標を持たない。** 空港は `traffic.ts` の `AIR_ROUTES` の

89:1 を保つには長さ 1.65ユニット＝178px＝円盤の41%**（＝5,250kmの滑走路）に

この嘘を運べるから。

**26/186都市が水上にある問題（§2-11）と同じ罠が空港にもある。**
12端点のうち**2つ（ホノルル・シドニー）が標高ラスタ上で水**、さらに4つが

滑走路の半分がレジンの上に出る。ホノルルは**708kmの滑走路がオアフ島に
どう回しても載らない**ので**サイトごと落とした**。港18件のうち4件も水上判定。

### 2-29. オーロラ（G50、完了）

**カーテン。光の塊ではない。** §2-21 の判断（形のない光は入れない）が
そのまま効く項目なので、極を囲む楕円帯から垂れる**縦の薄板**として作った。
1メッシュ・**ドローコール+1**（147→148）、3,600頂点。

**§2-12 が設計を決めた。** キーライトは固定なので明暗境界は動かない ——
太陽・北極の内積は**恒久的に +0.595**、南極は **−0.595**。つまり
**南のオーロラだけが常に夜側**。両方の楕円は作ってあり（コストは同じ）、
北側は8回転中2回だけ縁から覗く。

余緯度は教科書的な23°ではなく**30°**。カメラと台座を遮蔽物として実測し、
23°では可視サンプル30%、30°では40%。真鍮の襟を越えるだけの張り出しが要る。

**「後ろ半分しか描かない」は構図上の判断で、絵を見て決めた。**
南の帯は球の下端＝真鍮の襟と胡桃材の台座がある所に垂れる。加算合成なので
**手前側のカーテンが木の上に緑の光を塗り**、球が「台に載った物」ではなく
「台に重ねた透明画」になった。**リムの向こう側だけ**にすると、
惑星のシルエットに切られて縁から立ち上がる、実際に横から見たオーロラの
読みになる。

**半円にしたのは構図の算数でもある。** 半径2.66の全周環は最高点が中心の
2.66上＝画角の20.76°（半画面は20°）で**切れる**。北のピンで終わる弧なら
最高点はピン自身＝19.15°。ピンは頂点から23.4°回った所にあるから収まる。

球は 458px → 431px（−6%）で、なお画面高の半分以上。

**明暗境界は動かない（§2-12 の再確認）。** 指標は |sun·viewDir|（§2-18 の
0.567 をこの式で再現: 0.568）。**0.568 → 0.558、ディスク半径の 0.011 =
1.1px。** 球を上げると 0.556 に下がり、カメラを引くと 0.570 に上がるので、
2つの変更が偶然ほぼ打ち消し合っている。

**踏んだ地雷2つ（どちらも計測でしか出ない）:**

1. **Euler の既定順で球は歳差する。** `globeGroup` は z=地軸傾斜・y=自転を
   持つ。既定の XYZ は Rx·Ry·Rz と合成するので z が内側に入り、**傾いた球を
   ワールドの鉛直まわりに回す**＝極が円錐を描く。実測で**1/4回転で32.6°、
   半回転で46.8°** 棒からずれる。傾斜が0.04ラジアンの間は誰にも見えなかった
   バグで、**極に棒を通した瞬間に致命傷になる**（棒は台座に固定なので動く極を
   追えない）。`rotation.order = 'ZYX'` で全4象限0.0°。
2. **球を浮かせたらオーロラが台座に緑のリボンを敷いた。** §2-29 の
   `behind` 項は球の手前側しか消せない。球の**下**は、これまで真鍮の襟が
   塞いでいたので問題にならなかっただけで、3cm浮かせて44pxの隙間が開いた
   瞬間に向こう側のカーテンが透けた。深度テストも効かない（台座上面の手前半分
   はカーテンの前、奥半分は後ろ）。**ワールド高さで切る**のが正解:
   −1.25で消える（球の下端 −1.14 の 0.1 下）。

**費用: ドローコール 162 → 163（+1）**、三角形 +232。マウント全体（棒・弧・
座金2つ）が1マテリアルにマージされて1コール。**測り方の注意: `animate()` は
球ができる前から回っているので、組み立て中のフレームを混ぜると
min 12 / median 52 / max 163 になる。組み立て後だけで 162/163 は安定。**

**真鍮は銘板と別マテリアルにした。** 銘板の値（metalness 0.55 /
envMapIntensity 1.8）は**正面を向いた小さな平板**用の調整で、長い曲面に
着せると全方向が同時に環境を拾って**一様な蛍光オレンジ**になる（作って撮って
確認した）。マウントは metalness 0.8 / roughness 0.34 / env 0.6 —

**(1) 草原が砂漠に分類されていた。** 草の判定が

**(2) ケッペンは「育ちうるもの」であって「そこにあるもの」ではない。**
農地のラスタは無いが、地理はある: **人は平らな土地を耕し、住んでいる所を耕す。**
片方だけでは必ず壊れる（実測）:

- **平坦だけ**ではアマゾン(0.0032)・コンゴ(0.0036)・シベリア(0.0040)が消える
  ——地球で最も平らな森3つ。
- **人口だけ**ではアパラチアが消える。**habitability はアパラチア0.842 に対して

積は測った16地域すべてを分離する。→ `openLandAt(dir)` = max(気候由来の草原,
平坦×定住)。`canopyAt` がこれを読むので、**林冠を見て間引く全レイヤーが自動的に
追従する**。

**(3) Poisson-disc なので、上の2つだけでは画面に出ない。** §2-23 の教訓の再演。
しかも**線形の lerp では全部が同時に動く**: prairie が prairie に見えるまで
広げると**惑星の木が40%消えて、それでも3.5倍**しか稼げなかった。
→ **smoothstep**（0.05〜0.7）。閉じた林冠は詰め込み律速で、気候が支えなくなる
まで閉じたまま、そこから急に開く——それが本物の森の振る舞い。
草も同じ理由で可変間隔にした（**固定間隔ではカザフ草原1.83 対 アパラチア2.74 で、
森の中の方が草が多かった**）。

コーンベルトを0.37 で間引いていた**（＝動かしてはいけない方を最も強く引いていた）。
北米が均一だった理由の大半がこれ。

**正直な残り**: 太平洋岸北西部 0.17（目標0.59）と南東部の海岸平野 0.17（目標0.65）。
どちらも入力の限界 — **Csb はダグラスファーの海岸とイングランドの低地を同じ1クラス**
に入れるし、「平坦・高密度に定住・なのに55%が植林地」はケッペンと標高では農地と
区別できない。

### 2-34. その都市がまだ「いまいち」だった理由（G43 の作り直し）

§2-33 は3回サイズを直したが、**3回とも比較対象を間違えていた。**
レンダを見れば一目で、**都市は森の中の茶色い泥の塊**に見える。

**(1) 幹と比べていた。** §2-33 は「ブロック 2.4〜4.1px 対 幹 1.4px」で
足りていると判断した。だが建物の隣に立っているのは幹ではなく**木そのもの**で、
`broadleaf` の樹冠は半径0.03を1.15倍した球 = **0.069単位、約7px**。
つまり**全ブロックが木の半分の幅**で、都市の塗り全体(9〜16px)が樹冠1〜2個分 —
**都市が、その中に立っている木1本より小さかった。**
地被物にサイズで負けている物体は、色や高さでは救えない。

**(2) 屋根が名所と同じマテリアルだった。** ブロックは `stone` の壁に `roof` の
笠。`roof` は**寺の瓦の焦げ茶(#7a6249)**である。地球儀を**上から**見ると笠が
見えるものの大半なので、186都市が茶色い塊になった。パゴダと笠を共有している
限り、色の付け替えでは直らない。`±0ドローコール` はここでは**節約ではなく
制約**だった。

**直したもの:**

| | 前 | 後 |
|---|---|---|
| 塗りの半径 | `0.015 + size*0.023`（9〜16px） | `0.022 + size*0.034`（**22〜33px**、樹冠3〜5個分） |
| ブロック幅 | 2.4〜4.1px | **5〜7.5px（樹冠1個分）** |
| 配置 | ランダム散布＋ランダム回転 | **都市ごとに1つの街路方位を持つ格子** |
| 壁/屋根 | `stone` / `roof`(焦げ茶) | 専用マテリアル、頂点色。**屋根が一番明るい** |
| 区画 | なし | ブロックごとに暗い敷地板（淡い建物が映える相手） |
| ドローコール | ±0 | **+1**（都市専用の1メッシュ） |
| 都市 | 186 | **186**（脱落0） |
| ブロック | 2,136 | 1,637（**数は減、1個あたり面積は約4倍**） |

**格子が効くのは色より形だから。** 5pxでは箱1個の形は残らないが、
**辺の向きが揃った四角の集合**は残る。散布はどこまで行っても「粒」で、
これが §2-33 に唯一無かった要素。

**足場を2段にした（重要）。** 塗りを1.5倍にすると**中心の footprint 判定も
1.5倍になる** — 広い方のリングだけでは186都市中**2つが判定に落ちて消えた。**
直そうとした問題より悪い。**入らない場所には0.78倍の小さい町を出す**ように
して脱落0に戻した（88都市がこの小さい方を取っている。海岸都市が内陸に
追い出されずその場に残る、という意味でもある）。

**罠として残しておく:** 「小さすぎる」の判定は、**隣に実際に立っている物**と
比べること。幹・実寸・px数の絶対値ではなく、**同じ絵の中の競争相手**が基準。

「草原が無い・砂漠が砂漠に見えない・道路が無いから都市に見えない」への対応。

**(1) 林冠が12重に重なっていた。** 樹冠は0.069単位（7px）なのに

間引きに使っているのと同じ場）で**塗り**に入れた。草は2.4pxに拡大して

### 2-37. アーモンドはまだ居た（稜線の高さプロファイル）

§2-13 が記録し §2-23 が作り直したはずのアーモンドが、**まだ出ていた。**
コードのコメントは「稜線は端まで幅を保ってから丸める」と書いてあり、
**幅についてはその通り**だった：

    widthProfile  = (1 - a^7)^0.4   → a=0.8 で 0.91、a=0.9 で 0.77

**高さが直されていなかった。**

    heightProfile = (1 - a^2)^0.8   → a=0.7 で 0.58、a=0.9 で 0.27

これは**楕円**、つまり縦に立てたレンズである。そして**この大きさで目に入るのは
砂の上の輪郭ではなく「光の当たった上面」**なので、楕円の稜線の上面は
**尖った長円＝アーモンド**になる。§2-23 は輪郭（平面形）だけを直し、
**陰影の側に同じ形が残っていた。**

    heightProfile = (1 - a^6)^0.45  → a=0.7 で 0.95、a=0.9 で 0.71、端で0

実測（真上からのダンプ）：中央0.0170 / 70%地点 0.0098 → **0.0160**、
92%地点 0.0037 → **0.0110**。あわせて meander を 0.5 → 0.28
（自分の幅の半分ぶれるのは「幅のごく一部」ではなく、稜線が葉の形に曲がる）。

**この節の教訓は測り方の方。** 惑星を1周焼くと5分かかるが、
**砂丘のブロックを `node` にコピーして真上からの幅と高さを表で出せば数秒**。
形の問題は惑星のレンダではなく**単体のダンプで見ること**。
（`three` は素の node で import できる。WebGL も terrain も要らない。）

### 2-38. アーモンドの本当の原因は形ではなく配置だった（エルグの作り直し）

§2-37 で高さプロファイルを平らにしたら、**「割れたアーモンド」になっただけ**
だった。指数をいじっていたのが根本的に間違いで、**問題は形状ではなく配置**。

砂丘は他の全species と同じ Poisson 散布に乗っていた。つまり1個ずつ
**ランダムな位置・ランダムな縮尺（0.6〜1.45）・±0.225rad のランダム方位**で
置かれ、しかも**1個ごとに両端が地面に沈む**形をしていた。これは
**隣とつながらないことを3重に保証している**。エルグは「物の集まり」ではなく
**1枚の連続した波板**なので、この配置である限りどんな断面形でも
「砂の上に転がっている物体」にしかならない。

**分担を作り直した:**

| | 担当 |
|---|---|
| モデル | **断面のみ**。両端は平らに切る（隣と突き合わせるため）。meander 廃止 |
| 配置 | `placeErgRidges`：`duneBearing` に沿って**歩き**、セグメントを連ねる |
| 曲がり | 歩きが場を読むので**尾根全体が曲がる**（各個体が独立に揺れるのではなく） |
| 縮尺 | **尾根単位で固定**（個体ごとだと隣と合わない＝これが「割れ」の正体） |
| 端の減衰 | モデルではなく**尾根の端**で（歩き終わった実長から算出） |

**踏んだ計算間違い（レンダ前に発見）:** モデルはワールド単位（球の半径2）で
作られているので、長さ0.1のセグメントは **0.05 rad** を張る。歩きを 0.1 rad で
進めると**セグメント間隔が長さの2倍＝破線**になる。`STEP = 長さ / radius`。

**計測してから広げた:** 90,000点の一様シードのうちエルグは **1,197点＝球面の
1.3%**。最初のピッチ(0.034)と長さでは**充填限界が約115本**で、実際131本
だった（歩きは失敗していなかった＝場が狭すぎただけ）。ピッチ0.021、
長さ0.064、ゲートを**塗りの `sand` と一致**（erg>0.46 / arid≥0.74）にして642本。

**不変条件:** `RIDGE_PITCH < STEP × 最小scale`。これを破ると
**尾根が自分の次のセグメントをハッシュで弾いて全部1本になる**。
どちらの数字を見ても分からないのでコードにも書いた。

**その後（同セッションで解消）:** セグメントを連ねる方式そのものをやめ、
**尾根1本を1本の掃引ストリップ**にした。断面（7点のプロファイル）を歩いた
経路に沿って運び、隣り合うステーション間を四角形で張る。**継ぎ目は隠すのでは
なく存在しなくなる。** 経路は歩幅とは独立に3分割して補間（歩幅はハッシュの
`RIDGE_PITCH` に縛られるが、滑らかさを縛る理由は無い）。惑星全体で
**1メッシュ＝インスタンス版と同じ1ドローコール**。

### 2-40. 砂丘がヘビに見えていた（長さと横のピッチ）

**(1) 長すぎた。** 尾根は最大90ステップ歩けた。1セグメントは 0.0275 rad で、
出荷カメラでは **1 rad ≈ 204px** なので 5.6px。90ステップは**エルグを横断する
1匹の虫**である。片側3〜4ステップ（端から端で約34〜45px）に制限した。

**(2) 横のピッチが幅より狭く、隣同士が融合していた。** ピッチ 0.021 rad は
半径2の球で **0.042ワールド単位**、断面の幅は **0.05**。つまり重なっていた。
砂丘原は「峰」と同じくらい「峰の間の砂」でできているのに、それが無かった。

ピッチを広げられなかったのは「**ピッチ < 歩幅 × 最小scale**」という不変条件
（§2-38）のせいだが、これは**解き方が逆だった**。ハッシュへの登録を
**歩いている最中ではなく尾根が完成してから**に変えれば、尾根が自分自身を
弾くことは起こり得ず、**ピッチは自由になる**。不変条件は守るのではなく消した。

**(3) 幅がすべてを縛っていた。** 幅 0.03（＝0.05ワールド）だとピッチをそれ以下に
できず、エルグが持てる尾根の本数が頭打ちになる。さらに**最短の尾根が幅の3倍
＝菱形**（アーモンドの別の帽子）だった。幅を 0.018 にしてピッチ 0.023、
最短12ステーション（幅の約6倍）に。**尾根は幅の6〜12倍**という
線状砂丘の比率になった。

### 2-39. 高緯度の森が広葉樹に見えていた（タイガの形）

「ロシア中央部やカナダ北部にあんなに木が生えているのか、広葉樹に見えるが」
という指摘。**両方その通りだった。**

林冠レイヤーは**惑星全体で1つの形**（変位させた球）しか持たず、針葉樹は
その球を **0.78幅 × 1.35高** に潰して作っていた。コード中のコメントは
「タイガとジャングルの違いは**すべて**プロポーションだ」と書いていて、
**側面から見る限りはその通り**である。だが**地球儀は上から見る**もので、
**法線方向の引き伸ばしは唯一見えない軸**だった。結果、シベリアとカナダ北部は
熱帯と同じ丸い広葉樹の塊が少し細くなっただけのものになっていた。

**上から見て効く手がかりは「粒の細かさ」と「尖り」。** トウヒの樹冠は数m、
オークは15〜20m。針葉樹に**円錐のバリアント**を与え（同じノイズ、変位は
控えめ＝円錐でなくなるので）、幅を 0.62 にして粒を細かくした。
リムでは初めて**スパイア**として読める。

**ドローコールは±0。** バリアントを増やさず**割り当て直した**
（粗3つのうち1つ、細2つのうち1つを針葉樹に）。バケットも
ラウンドロビンから**気候による振り分け**に変更（形がバリアントになったので、
広葉樹のバケットに入ったトウヒは広葉樹として描かれてしまう）。

**もう半分は「森林限界が無かった」こと。** 林冠は
`COLD_TEMPERATURE_LIMIT = 0.02` まで生えるのに、塗りは
`TUNDRA_TEMPERATURE = 0.14` 未満でツンドラになる。**その間は
「ツンドラとして塗られた地面に森が立っている」**状態で、氷まで続いていた。
ケッペンは ET を 0.05（ほぼ無立木）と言っているが、**このレイヤーは
Poisson ディスクなので確率を聞かない** — canopy 0.05 でも疎な間隔で林が立つ。

森林限界は等高線ではなく数百kmかけてほつれるので、**間隔（ディスクが従う
唯一の量）**に乗せた。`treeLine = smoothstep(temp, 0.045, 0.175)` で
寒冷端は間隔5倍＝**密度1/25**。実測（温度帯別の 木/陸地候補）：

| 温度帯 | 陸地 | 木 | 木/陸 |
|---|---:|---:|---:|
| 0.00–0.05 | 54,207 | **0** | 0.0000 |
| 0.05–0.10 | 18,128 | 30 | 0.0017 |
| 0.10–0.15 | 16,107 | 232 | 0.0144 |
| 0.15–0.20 | 17,003 | 338 | 0.0199 |
| 0.45–0.50（熱帯） | 114,272 | 1,234 | 0.0108 |

**円錐の高さは 0.16 → 0.10。** 広葉樹の塊が地上0.039なので、0.16 では
**全体の3倍の高さ**になり、リムに横向きの棘の壁ができた
（サバンナの木で同じ失敗が記録されている）。広葉樹の2倍で十分。

**ここで最後のアーモンドが出た:** 端の減衰を「9ステーション」と固定していたので、
**18ステーション未満の尾根は端から端まで減衰＝レンズ**になっていた。
減衰を尾根自身の長さの15%に比例させ、**12ステーション未満の尾根は破棄**
（短すぎる尾根は、どう整形してもアーモンドにしかならない）。

### 2-39. 川（G27 完了）

§2-8 が予告していた通りだった。**原因は3つとも診断済みで、修正は全部その通りに効いた。**

| | 変更前 → 変更後 |
|---|---|
| 陸地セルのシンク | **12.6% → 0%**（優先度フラッド） |
| 全球最大流量 | 242 → **1,338** |
| アマゾン | 22（強度0.000）→ **1,206（強度1.000）** |
| コンゴ | 33（0.007）→ **493（0.899）** |
| ナイル下流 | 8（0.000）→ **171（0.572）** |
| サハラ／アラビア／豪州内陸／ゴビ | 35/1/0/1 → **全部 0** |

**(a) 窪地埋め。** D8 の落とし口探索が厳密な `<` で窪地埋めが無かったので、
陸の12.6%がシンクだった。優先度フラッド（Barnes ほか）で海岸から埋め、
**epsilon の傾きを付ける**（付けないと埋めた盆地が今度は「平ら」で水が溜まる）。

**(b) 各セルの重みは「1」ではなく降水量 × セル自身の面積。** G33 の
`precipitationAt` から `max(0, precip - 0.3)` を取る。**閾値であって傾斜ではない**
のが要点で、これが無いと砂漠も熱帯雨林と同じ形の水系を薄く持つ。
面積項（sinθ）も同じくらい重要で、これを忘れると**シベリアがアマゾンの
流量を持つ**。ナイルが砂漠を越えて残るのは上流から満量で届くからで、
これは仕組みの副産物であって特別扱いではない。

**(c) 塗りの ramp は定数ではなく分位点で持つ。** 旧コードの
`(ln(flow+1) - 3.4) / 2.5` は既に存在しない流量分布に合わせた定数で、
**射程を外れたときに何も起きない（＝静かに失敗する）**。分位点なら外れない。

**時限爆弾は爆発前に外した。** `deltaCoast` を `terracedElevation` から
**生の海抜**（`SEA_LEVEL + 0.008`）に変更。実測でこの帯は陸の12.6%、
かつ強い川を持つセルの60%＝河口。旧式のままなら砂色がアマゾン盆地を
内陸3,000kmまで塗っていた。

#### ここで新しく踏んだもの

- **川はセルではなく線である。** 流量グリッドをテクセルごとに引くと、D8 が
  対角に進むたびに**四角が角でしか接触せず、アマゾンが青い長方形の列**になる。
  ramp をどう調整しても直らない。**リンクを線分としてラスタライズする**
  （幅は流量から、端は1テクセルでフェザー）。これで網の粗さは
  「線の品質」ではなく「形」のコストになり、水系グリッドは粗いままでよい。
- **可視セルを「割合」で決めると、格子を細かくした分だけ網が伸びる。**
  同じ分位点で 384→768 にしたら**アマゾン盆地が青一色**になった。
  ある長さの網を表すセル数は格子の細かさに比例するので、
  **分位点は `384/width` でスケールさせる**。
- **「水路から木を追い出す」だけでは川は見えない。**（§2-35 の道路と同じ罠の
  一段深いところ）センサスで**16,000本中1本も水路に立っていない**ことを
  確認したのに、レンダのアマゾンは**完全に閉じた林冠のまま**だった。
  樹冠が11テクセル、水路は4テクセル。**対岸に正しく立っている木が、
  川と手前の岸をまとめて覆う。** 伐開すべきは水面ではなく**回廊**で、
  同じ網から**幅5倍の第2ラスタ**（`riverCorridorAt`）を焼いて木だけをそれで
  間引く（草と塗りは細い方を読む＝両者は同じ網なのでズレない）。
  代償は全球の木 −10%。これで初めて川が「林冠の切れ目」として読める。

### 2-40. 湖（G28 完了）— 「正しいのに見えない」を4回積んだ

**湖は標高ラスタに存在しない。** 実測: 五大湖 0.0819、アイオワ 0.0843。
出典が地形＋水深の合成なので、内水面は周りの地面と同じ値で塗られている。
カスピ海だけは海面下なので水深側に写っている。つまり**水系をどう改良しても
出てこない**ので、都市・港・火山と同じく**実座標テーブル**で置く（19湖）。

**入れる場所は `heightAt` の最後。** 「海と同じ扱いにならない」への答えが
そのまま「盆地を掘る」になる。掘れば海シェルが覆い、海岸距離場が岸を作り、
塗りが海底として読み、散布が木を立てず、都市が後ずさりする——
**どれ一つ湖の存在を知らなくていい。** `min` で掘ること（カスピ海と
マラカイボは既に水なので、持ち上げる可能性を残すと台地ができる）。

#### 見えるまでに4回外した。全部「別のサブシステムが正しく動いた結果」

1. **白波が湖を埋めた。** 白波は§2-10 で「深さではなく岸からの距離」に
   したもの。**小さい湖は全域が岸**なので、湖が丸ごと泡になり、しかも
   泡はシェルのアルファを上書きするので**不透明な白い塊**になった。
   汀線の内側で切る。
2. **湖が井戸の底にいた。** `displayHeight` の `coastalStep` は
   レリーフ地球儀の彫り込みで、実測**8.4px**。大陸には効くが、
   数pxの湖には**湖幅と同じ高さの壁**になる。実測でビクトリア湖は
   水面がシェルの0.84px下、周囲は8.4px上。岸で1/5に落とす。
3. **シェルは湖の上に2.8%しか出ていなかった。**（海を不透明マゼンタに
   差し替えて撮った）球は384分割＝1クアッド0.0164 rad。当時の湖は
   水面が0.028 rad＝**2頂点**しかなく、メッシュが即座にシェルを突き抜ける。
   → **この大きさの湖は「樹脂越しの海底」ではなく塗りで水にする。**
   塗りは2048テクセルあるので解像度の問題が無い。
4. **樹冠が湖の上で閉じた。** 川と同じ（§2-39）。しかも**伐開の到達距離**が
   足りていなかった: 汀線基準で伐ると 1.2 湖半幅に立つ木が生き残り、
   樹冠半径3.5px が半径6.5px の湖に届く。**伐開は「湖＋樹冠1つ」まで**
   （`lakeShoreAt`、1.9半幅）。

**それでもまだ小さかった。** 1クラウン幅（0.018 rad）ではビクトリア湖が
6pxの水たまりにしかならず、タンガニーカは暗い糸だった。**下限を0.030 rad
＝12px＝樹冠3つ**に上げ、大きいものは順位を保って比例拡大（カスピ0.055、
スペリオル0.042、ビクトリア0.045＝実寸の約2倍）。これで初めて読める。
副産物として**シェルも湖を覆うようになる**（2頂点→5頂点）。

**教訓:** 「データは正しい」「塗りは正しい」「散布は正しい」が全部同時に

### 2-44. 起動時間、第一歩（G32 一部完了）— ゼロ係数のノイズを呼ばない

**§2-42 の候補1「低周波のfbm3をベイクする」に着手し、2つだけ直した。
両方とも1コマンドのピクセル差分で確認した。**

`--cpu-prof` で見ると、`noise3` の自己時間の内訳を呼び出し元へ遡って
帰属させたとき、`heightAt` だけで noise 系の 7.0%（全体の 20.6% のうち）を
持っていた。中身を見ると理由は単純：`rugged`（山の岩肌ノイズ、4オクターブ）と
`midRelief`（中間起伏、3オクターブ）は**係数が0になる場所でも毎回計算していた**。

- `rugged` は `ruggedAmount`（`smoothstep`）を掛けてから使われる。
  `smoothstep` は下限以下で**厳密に0**を返すので、海のような
  `macro <= SEA_LEVEL + 0.04 - beltBoost*0.05` な場所では
  `rugged` の値そのものが結果に一切効かない。
- `midRelief` も同様、`landMask`（`smoothstep(macro, SEA_LEVEL, SEA_LEVEL+0.1)`）
  を掛けており、外洋（`macro <= SEA_LEVEL`）では厳密に0。

**惑星の72%が海。** どちらも「計算してから捨てる」を「係数が0なら呼ばない」に
変えるだけで、結果はビット単位で不変（0を掛けるので中身は関係ない）。
`terrainColor:2345` の seabed mottle のすぐ下に既にあった

というコメントと同じ手を、`heightAt` にはまだ適用していなかった、というだけの話。

ついでに `ergAt`（「この中で意図的に一番低周波なフィールド」と元から書いてある）

実測では砂漠の縁に**±1/255のピクセルが全体の0.05%**に散るだけ

### 2-45. 都市の陸寄せを一本化（G48 一部完了）— 建物と塗りが別々に動いていた

**「港は湾に、都市は川沿いに」の前半、コンシステンシーの分から着手。**
川沿いの方は未着手（下記）。

§2-11 が測っていた「186都市のうち26都市の中心座標が水ピクセル」は、
`landmarks.ts` の `placeCityBlocks` がとっくに個別に直していた——
`nudgeToLand` で建物だけを陸へ動かしていた。だが `terrain.ts` の
`urbanAt`（昼の灰色塗装・夜の灯り・植生の伐採の単一の真実）は
`MAJOR_CITIES` の生座標をモジュール読み込み時に即座に固定していて、
**同じ陸寄せを一度もやっていなかった。** 結果、水上に立つ26都市は
建物と塗り・灯りが**それぞれ独立に「陸へ動く」判断をし、別の場所へ動ける**
状態だった——この関ファイルの `cityPatch`/`cityPatchRadius` のコメントが
名指しで警告している「2つの表現が食い違う」パターン（雪線と雪片の分裂）
そのものが、位置については直っていなかった。

**直したのはモジュール読み込み順の問題でもある。** `URBAN_FEATURES` は
トップレベルの `const` で、`main.ts` の `await loadRealElevationData` より
**前に**（importの評価順で）走る。だから陸寄せをここでやろうとすると
`heightAt` はラスタ未読み込みの平らな世界を見ることになる——
`bakeField` 系がすでに使っている遅延初期化（`??=`）と同じ形にして解決。

- `resolvedMajorCities()`（新規、遅延・メモ化）が `MAJOR_CITIES` の各都市を
  `heightAt` で陸へ寄せる。半径は `landmarks.ts` の `placeCityBlocks` が
  実際に使っている値（`cityPatchRadius(size)*0.62*0.6` と `*0.78` の
  二段構え）を**そのまま流用**——最初、生の `cityPatchRadius(size)*0.6`
  で試したら186都市中100都市が動き、大阪や札幌のような明確に陸地の都市が
  最大5.25度も動いた。原因は判定に使う輪の半径が実際の判定（`placeCityBlocks`
  の0.62*0.6倍）より6割広く、大阪湾のような実在する入江を「町を置く余地が
  ない」と誤判定していたため。半径を合わせたら186都市中72都市に収まった。
- `URBAN_FEATURES`/`URBAN_BUCKETS` も遅延化（`urbanFeatures()`/
  `urbanBuckets()`）し、`resolvedMajorCities()` を経由するようにした。
  `landmarks.ts` の `placeCityBlocks` も同じ関数を読むよう変更——
  自前の `nudgeToLand` 呼び出しはそのまま残している（個々のブロックの
  足場を確かめる仕事はこれが必要）が、渡す中心座標が既に解決済みなので
  ほぼ毎回 `moved: 0` で即決着する。

**検証（node シム）:**

| | 変更前（`placeCityBlocks` 単独） | 変更後（共有テーブル） |
|---|---|---|
| 建物側の `nudged`（`CityStats`） | 72 | 0（センターが既に解決済み） |
| `resolvedMajorCities()` の移動数 | — | 72（一致） |
| 最大移動量 | — | 3.15度 |

塗りの前後差分（2048×1024平面展開図）は**16,816px（0.80%）**、島や海岸沿いに

ではなく、動いた72都市の位置に一致する）。Playwrightでの実機レンダーも

**「都市は川沿いに」は未着手。** `riverAt`/`riverCorridorAt` は水の有無の

**検証**: シェーダコンパイルエラー無しで Playwright実機レンダー、極地の

### 2-59. 雲の層の重なり（G55、完了）

`hoverBase` は種別ごとに既に違う（積雲0.16・層雲0.09・巻雲0.34）が、
それが画面上の**重なりの表現**に一度も結び付いていなかった。新しい場を
作らず、地面の影に既に使っている雲量マップ（`buildCloudShadowTexture`が
一度だけ焼く被覆＋移流率マップ、globeとoceanが読んでいるのと同じもの）を
**雲自身の材質**にも読ませた。`regularByVariant`/`stratusNodules`/
`cirrusNodules` の core メッシュは全部 1つの共有 `coreMaterial` を使って
いる（`buildLayer`参照）ので、そこに `onBeforeCompile` を1回足すだけで
積雲・層雲・巻雲すべてに効く。頂点シェーダで instanceMatrix 適用後の
`transformed`（＝そのナジュールがグローブのオブジェクト空間で実際に置かれた
位置）を正規化して方向 varying にし、フラグメントで main.ts/ocean と同じ
`cloudShade()` を強度0.3で呼んで `diffuseColor` に掛けるだけ。デッキの
下・周囲の被覆が濃い場所にあるナジュールほど僅かに暗く沈み、層の厚みが
読めるようになる。巻雲がまばらな自分自身の被覆で自己遮蔽されるのは
物理的にやや過剰だが、巻雲は不透明度が低くほとんど読めない。

**副産物**: `CLOUD_SHADOW_GLSL`（`cloudShade`/`rainWet`）を main.ts から
clouds.ts へ移し `export` した——このテクスチャを最初に焼く側が定義も
持つべきで、main.ts はそれを消費するだけの立場になった。

**検証**: 一時的に強度を0.98へ上げてレンダーし、雲の塊がグレーに沈む一方で
輪郭や個々のナジュールの形は壊れないこと（真っ黒や色反転にならないこと）を
確認。本番値0.3に戻し、tsc・build・Playwright実機レンダーでコンソール/
ページエラー無しを確認。

### 2-61. エルグを実座標に（G6、完了）

`rawErgAt`（塗りと砂丘散布が両方読む唯一の場、docstring 通り）は

ノイズが「その中でも砂丘か隙間か」を決める。どの領域からも外れる点は

省略（G32、§2-44）と同じ形の副産物。

**`ergAt`が塗りと`species.ts`の両方から読まれる一本の場だったおかげで、
このファイル1関数の変更だけで塗りも砂丘の実体（散布・尾根）も同時に
実座標化された**——2箇所が別々にドリフトする心配がそもそもない設計に
なっていた。

**検証**: 6つの実座標の中心で`ergAt`を実測（0.615〜0.809）、6領域の
どこにも入らない既知の非エルグ砂漠（カラハリ・ゴビ・アタカマ）で正確に
0.000であることを確認。node シムで2048×1024の平面展開図を焼き、
サハラに離散した2つの明色パッチ（グラン・エルグ、エルグ・シェシュ）、
アラビア半島に1つ（ルブアルハリ）、中央アジアと豪州中部にそれぞれ1つ
（タクラマカン、シンプソン）が実際の位置に現れ、それ以外の砂漠部分
（サハラの大部分、カラハリ）が礫砂漠の色のままであることを目視確認。
tsc・build・Playwright実機レンダーでコンソール/ページエラー無しを確認。

## 3. 構造的な問題

> **気象の「発生源」が一元化されていない。**

雲は雲用ノイズ、雪は緯度、雷は雲タイプ、乾燥度はケッペン、川は標高 —
5つが全部バラバラの根拠で動いている。だから「快晴なのに雪が降る」「雨は
降らないのに川がある」「雲が気候と無関係な場所に湧く」が同時に起きる。

あるべき姿は1つの気象場から全部を派生させること。
**これは `docs/design-memo.md` の当初の依存関係（層3 空＝雲・降水量 →
層4 バイオーム）そのもので、実装が途中で逸脱した形。** 復元にあたる。

```
ケッペン区分 ─┬→ 降水量プロキシ ─┬→ 雲量（どこに雲を置くか）
             │                  ├→ 雨（雲の下、暖候）
             │                  ├→ 雪（雲の下、寒候）
             │                  ├→ 雷（対流性の強い所だけ）
             │                  └→ 川の流量の重み
             ├→ 乾燥度 → 塗装・植生（実装済み）
             └→ 林冠密度 → 森林（実装済み）
```

降水量プロキシは**データがもう手元にあるので実装コストが小さい**のに、
雨・雪・雲・雷・川の5系統を同時に正す土台になる。費用対効果が最大。

## 6. 作業のやり方（踏襲すること）

- 検証は毎回 `npx tsc --noEmit && npm run build`
- ローカル確認は `(nohup npx vite preview --port 4173 --host > ログ 2>&1 &)` を
  **専用のBash呼び出しで単独実行**（pkillと同じコマンド内で起動すると
  レースコンディションで落ちる）
- ヘッドレス検証は Playwright（`/opt/pw-browsers/chromium`、
  `/opt/node22/lib/node_modules/playwright/index.js` は CommonJS なので
  `import pkg from ...; const {chromium} = pkg;`）。swiftshaderのため
  ビルド完了まで50〜70秒かかるが正常
- git: featureブランチにpush → `git fetch origin main && git merge-base
  --is-ancestor origin/main HEAD` で確認 → mainへfast-forward push
  （**mainへのpushでのみ自動デプロイが走る**）→ Actions の conclusion=success を確認

### 素の node でこのプロジェクトを回す（一番効いた道具）

**アプリ全体は swiftshader で 90〜110 秒。同じ塗りが node なら 6〜9 秒で焼ける。**
`buildTerrainTexture` などが要るのは WebGL ではなく **DOM の2つの API だけ**
（`Image` と `canvas.getContext('2d')` の `drawImage`/`getImageData`/
`putImageData`）。これを30行の shim で埋めれば、**本物のモジュールをそのまま**
node から呼べる（自前で式を書き写すと必ずズレるので、写さないこと）。

- PNG の入出力は `pngjs`（スクラッチ側に `npm i`）。`putImageData` を
  ファイル書き出しにすれば**平面展開図がそのまま PNG で出る**
- 型は `node --experimental-strip-types`。ただし `src/*.ts` の import は
  拡張子が無いので、`register()` で `.ts` を補う resolve フックが要る
  （`module.register` に10行）
- 一時的な `export function __xxxProbe()` を生やして内部関数を叩く。
  **コミット前に必ず外し、grep で確認**
- §2-39 の水系はこれで回した。分位点・シンク率・地域別流量の表が**1秒**で出る。
  §2-8 の実測値（シンク12.6%、最大242、アマゾン22、コンゴ33）が
  そのまま再現できたので、**着手前に「同じものを測れている」ことを確認できた**

### 計測フック（推測で判断しないための道具）

いずれも**一時的に仕込み、コミット前に必ず戻す**。

1. **植生センサス** — `species.ts` のメッシュ構築直前に
   `if (location.search.includes('debugveg')) window.__veg = {placements,
   forestPoints, grassPoints, points, screePoints}` を仕込み、
   Playwrightの `page.evaluate` で地域ごとに集計する。
   緯度経度への逆変換は **`lon = atan2(z, -x) * 180/π - 180`**
   （`-180` を忘れると地球の裏側を測ることになる。一度やらかした）
3. **フィールドプローブ** — `window.__probe = (x,y,z) => sampleAt(dir)` を
   同じ場所に仕込み、地域ごとに lat/lon 格子で叩く。「植生が置かれない」
   のが**どのフィールドのせいか**を切り分けられる。第1弾で本命の原因
   （中間レリーフノイズと海面グレー閾値）はこれでしか見つからなかった。
   緯度経度 → 方向ベクトルは
   `x = -sin(θ)cos(φ), y = cos(θ), z = sin(θ)sin(φ)`
   （`θ=(90-lat)·π/180`, `φ=(lon+180)·π/180`）
4. **ラスタの直読み** — `public/world-elevation.png` をブラウザの canvas に
   描いて `getImageData` し、既知の地域のヒストグラムを取る。
   **定数が本当にデータと合っているかは、これでしか分からない。**
   ELEVATION_SEA_GRAY が2つずれていたのはこれで判明した
2. **平面展開図** — `buildTerrainTexture` の `ctx.putImageData` 直後に
   `if (location.search.includes('debugcanvas')) window.__terrainCanvas = canvas`
   を仕込み、`canvas.toDataURL()` で抜く。3D投影より地理的正しさの判定が確実

## 9. 判断の記録（蒸し返さないために）

- **雲・飛行機・衛星に真鍮線の支持棒を立てる案**（外部レビューで「効果大・
  コスト小」と評価された）は**不採用**。この作品は浮遊感を一貫して排除して
  きた経緯があり、人工物を足す方向は逆行する。
- 外部レビューのうち、ライティングのデスクランプ化・雲シェーダの全面刷新も
  現時点では**不採用**。
- 大気シェル（白い薄膜）は過去に意図的に削除済み。復活させないこと。
- **周辺環境は「重厚な書斎」。明るくモダンな書斎を試して却下した。**
  シーンは暖色キーライト1灯＋極小のアンビエントで、これが球の「撮影された
  実物」感を作っている。淡い壁が自前の拡散昼光を持つと、硬い暖色ランプで
  照らされた被写体の背後に別光源の面が来ることになり、**2枚の写真を合成した
  ように見える。** 同じ1灯でフレーム全体を説明できるのは濃い胡桃材と低照度。
- **背景の壁は写真1枚（`public/study-wall.jpg`、Gemini生成）。** ジオメトリで
  作らない。被写界深度の外なので鮮明に見えることがなく、幾何を作るのは無駄。
  ただし**プレーンのサイズは「見える範囲」に合わせること** — 幅80で貼ると
  13ユニット奥・画角40°では画像の中央23%しか映らず、書棚が全部画面外に出る。
- **子午線環（球を囲む真鍮の半円弧＋目盛り）を一度削除した。**
  「地球儀の視覚文法」として追加したが、カメラ正面の平面に置かれた
  **球とほぼ同半径の**環はシルエット上の円に射影される。つまり真鍮が
  リムをぐるりとなぞり、球が「机に置かれた物」ではなく「枠の中に嵌った物」に
  見えた。
  **→ §2-31 で、依頼により別設計として作り直した（撤回ではなく限定）。**
  却下理由の3条件（球とほぼ同半径／全周／カメラ正面の平面）を全部外してある:
  半径2.66で**投影が半径2.0のディスクを一度も横切らない**（最接近2.542）、
  全周ではなく南のピン→左→北のピンの半分、そして半径を決めているのは
  球ではなく**雲**（不透明な雲が2.540まで届く）。
  **「環はダメ」ではなく「リムをなぞる環はダメ」が本当の教訓。**
  次に環を触るときは、まず投影の最接近距離を測ること。
- シャドウマップは実機クラッシュの原因として無効化した経緯がある（G26で
  復活を検討する際は、実機での安全域を見極めながら）。
