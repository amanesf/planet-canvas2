## 1. 前セッションで何が終わったか

**G32（起動時間）に一部着手。§2-44 に詳細。**

§2-42 が挙げた候補1「低周波の fbm3 をベイクする」を、実際にやる前に
`--cpu-prof` で `noise3` の呼び出し元を遡って帰属させ直した。結果、
一番大きかったのは「ベイクすべき低周波ノイズ」ではなく、**`heightAt` が
係数0（`smoothstep` の下限以下）でも `rugged`／`midRelief` のノイズを
毎回律儀に計算していたこと**だった。惑星の72%は海で、そこでは係数が
厳密に0になる。計算してから捨てるのをやめて、係数が0なら呼ばない
だけに変えた——結果はビット単位で不変（0を掛けるので中身は関係ない）。
ついでに `ergAt`（「意図的に一番低周波」と元から書いてある）を既存の
`bakeField`/`sampleField` に載せた。こちらは砂漠の縁に±1/255が0.05%だけ
散る（許容範囲、位置も確認済み）。

| | 効果 |
|---|---|
| **`heightAt` のゼロ係数ノイズ削り** | ビット単位で無変化（差分0テクセル） |
| **`ergAt` のベイク** | ±1/255 が全体の0.05%（サハラ等の砂漠の縁のみ） |
| **`buildTerrainTexture` 計測（node シム）** | 2048×1024で **13.4%短縮**、既定の1536×768で **8.2%短縮** |

**noise3 の残り**（`LinearToSRGB`・`coastlineJitter`・`canopyWarp`・
`paintGrain` 等）は §2-44 の最後に理由付きで書いてある。特に後半3つは
**意図的に高周波**（粒状感・階段のほぐしがそのものの目的）なので
ベイク対象から外したこと。同じ勘違いをしないこと。

**続けて G48（都市と地形の整合）の前半にも着手。§2-45 に詳細。**
`landmarks.ts` の `placeCityBlocks`（建物）は前から自前の `nudgeToLand` で
水上都市を陸へ動かしていたが、`terrain.ts` の `urbanAt`（塗り・夜景・
植生伐採の単一の真実）は動かしていなかった——186都市中72都市で、建物と
塗りが**別々に**「陸へ動く」判断をしていた（雪線と雪片の分裂と同じ形の
バグ、位置版）。`resolvedMajorCities()`（新規・遅延初期化）に一本化し、
両方がこれを読むようにした。**最初の実装は判定の輪の半径を実際より6割
広く取ってしまい、大阪や札幌のような明確な陸地の都市まで最大5.25度動かす
バグを作った**——`placeCityBlocks` が実際に使っている半径
（`cityPatchRadius(size)*0.62*0.6`、二段構え）に合わせ直して72都市・
最大3.15度に収まった。検証は landmarks.ts 側の `CityStats.nudged` を
一時的に出力して「変更前は72件・変更後は0件（センターが既に解決済み）」
を確認する形で行った。

**触っていない副産物**: `buildRoads`（G46）が `MAJOR_CITIES` の生座標を
使い続けているのを見つけたが直していない。`ROADS` はトップレベルの
`const` で、`resolvedMajorCities()` と同じ「ラスタ未読み込みのうちに
モジュール評価が走る」危険地帯にいる（§2-45 末尾に書いた）。うっかり
配線すると陸寄せキャッシュが空のラスタで固定される事故になるので、
道路の端点は今回意図的に据え置いた——72都市ぶん、道路の端点とパッチが
最大3.15度ズレている。

## 4. 地雷（同じ穴に落ちないこと）

**植生・都市で新しく踏んだもの（§2-32 / §2-33）:**

- **「多すぎる」と「どこも同じ」は別の問題。** 米本土の森は総量では
  むしろ不足していて、**分布が平坦なだけ**だった。総量を見る前に
  **地域ごとの比**を出すこと。
- **一つの閾値が2つの生物群系を巻き込む。** `arid<=0.52` が砂漠と草原の
  両方を切っていた（BW=0.90／BS=0.58）。**閾値を足す前に、その両側に何が
  居るかを表で確認する。**
- **効果の向きを確認せずに強度を上げない。** 農地の間引きは
  habitability 由来で、**アパラチアを0.62・アイオワを0.37** と
  逆向きに効いていた。強くしても悪化するだけだった。
- **地域ボックスの平均は非線形な場を隠す。** アパラチア(0.0140)と
  グレートプレーンズ(0.0148)は起伏の平均が同じ。山地だけの箱
  （ブルーリッジ）を切ったら 0.0216 で分離した。**箱が広すぎると
  「効いていない」と誤診する。**
- **レンダのレイヤー識別を「個数の順位」でやると転置する。** 調整で
  草と森の大小が入れ替わって、表が丸ごと逆になった。**ジオメトリ種別で
  名指しすること。**
- **小さい物は3回作り直す前提で。** 建物は 幅→高さ→凝集 の順に
  3回直した。**特に「木と同じ高さの物は森に埋没する」**。

**その3回が全部外れた理由（§2-34、都市の作り直し）:**

- **「小さすぎる」は、隣に実際に立っている物と比べること。** 建物を3回
  直したのに全部足りなかったのは、**幹(1.4px)と比べていた**から。隣に
  立っているのは幹ではなく**樹冠(7px)**で、全ブロックが木の半分、都市の
  塗り全体が樹冠1〜2個分だった。**px の絶対値でも実寸倍率でもなく、
  同じ絵の中の競争相手が基準。**
- **「上から見て何色か」でマテリアルを決める。** 壁を `stone`、笠を
  `roof`（寺の瓦の焦げ茶）にしたら、地球儀は上から見るものなので
  **都市が茶色い泥の塊**になった。**平らな屋根はその物体の一番明るい面。**
- **ドローコール±0 は、節約ではなく制約になることがある。** 名所と
  バケットを共有している限り色を直せなかった。**+1 で買えるものが
  大きいなら買う**（頂点色なら壁・屋根・タワー・敷地が1バケットに乗る）。
- **数ピクセルで残るのは色ではなく「向きの揃った辺」。** 散布はどこまで
  凝集させても粒に見える。**都市ごとに1つの街路方位を持つ格子**にした
  途端に「町」になった。
- **場を広げたら、その場を使っている判定も広がる。** 塗りを1.5倍にしたら
  中心の footprint 判定も1.5倍になり、**2都市が丸ごと消えた**。
  広げる変更では必ず**「入らなくなった物」を数える**。小さい代替
  （0.78倍の町）を用意して脱落0に戻した。

**生物群系（§2-35）:**

- **「Xが無い」の大半は「地面が見えない」だった。** 樹冠7pxに対して林冠の
  間隔が0.0057（**12重**）で、陸地が緑一色に埋まっていた。閉じた林冠は
  **樹冠が接すれば足りる**。増やす前に**重なりの深さ**を計算すること。
- **同じ罠を別のファイルでもう一度踏む。** 散布の `arid <= 0.52` と同じことを
  塗りの `smoothstep(arid, 0.4, 0.58)` がやっていた（**BSk = 0.58 で飽和**）。
  **片方を直したら、同じ量を読んでいる別のファイルを必ず見る。**
- **1pxの物は、比を何倍にしても見えない。** 草原は「草の密度」ではなく
  **「木が無い・地面の色が違う」**として読まれる。**マスで効くのは塗りだけ。**
- **線は点より安い。** 都市は22〜33pxの点だが、道路は2テクセル幅でも
  数百px走るので画面への寄与が大きい。ただし**塗るだけでは駄目**で、
  **林冠を伐開して回廊にする**こと（上から見えるのは路面ではなく木の切れ目）。
- **季節を止めないと色は比較できない。** 1分＝1年なので連続する2枚は別の月。
  `animate()` が毎フレーム書くので**代入では競合する** —
  `Object.defineProperty` で value を読み取り専用にする。

**§2-36 で踏んだもの（自分の作業手順のバグ）:**

- **`str.replace()` の戻り値を確認しないと、直したつもりの箇所が直っていない。**
  インデントが2桁違うだけで一致せず、**`butte` の 0.22 は3回「下げた」のに
  1度も変わっていなかった** — サハラのメサ畑はそれが原因。
  **置換は必ず `assert old in s` を通すこと。**
- **「浮いて見える」は塗りではなく法線の問題。** 標高ラスタ上サハラは実際に
  平坦なので `terracedElevation` がほぼ一定 → **メッシュがただの球面**。
  props で隠れている間は表面化しなかった。**入れる場所は `displayHeight`**：
  `displaceSphere`（頂点と法線）と `buildReliefField`（ドライブラシ）が
  両方これを読むので、**1箇所でジオメトリと塗りが同時に揃う。**
- **起伏の波長はメッシュの分解能から決める。** 球は384分割 = 1クアッド
  0.0164 rad。**4クアッド(0.065 rad)未満は表現できずエイリアスになるだけ。**
  ノイズスケール9（0.11 rad ≒ 7クアッド）を採用。
- **振幅は px ではなく「傾き」で決める。** この浅さの起伏は稜線ではなく
  **陰影**で読まれる。0.045 / 0.065 rad ≒ 20度。
- **フェードの閾値は測ってから置く。** `terracedElevation` の実測は
  サハラ西 中央値0.0187、エジプト 0.0118。0.02 までフェードさせると
  **エジプトだけ6割に減衰**していた（0.009 に変更）。
- **形の問題は惑星ではなく単体でダンプして見る。** 砂丘のブロックだけを
  `node` にコピーして真上からの幅・高さを表にすれば**数秒**（`three` は
  素の node で import できる。WebGL も terrain も要らない）。惑星を焼くと
  5分。**アーモンドの原因は表を1回出しただけで確定した。**
- **「輪郭を直した」は「見え方を直した」ではない。** 砂丘は平面形が
  修正済みだったのに高さプロファイルが楕円のまま残っていた。**この大きさで
  目に入るのは輪郭ではなく光の当たった上面**なので、アーモンドは
  シルエットから陰影に移っただけで残っていた。**同じ形状パラメータが
  2軸に分かれていないか確認すること。**
- **検証できない変更は入れない。** 球の分割を16→24に上げる案は、
  測定ツール（x でグループ化）が壊れて確認できなかったので**戻した。**
- **「形が変」の原因が形状にあるとは限らない（§2-38）。** 砂丘は断面形を
  2回作り直しても直らなかった。原因は**配置**で、ランダム位置・ランダム縮尺・
  ランダム方位・個体ごとの端の減衰の4つが**隣と繋がらないことを保証**していた。
  **「これは物の集まりか、1枚の連続した面か」を先に決めること。**
  面なら Poisson 散布ではなく**歩かせる**。
- **ワールド単位と角度を混ぜない。** モデルは球の半径2のワールド単位、
  歩きは単位ベクトル上の角度。長さ0.1は **0.05 rad**。
  混ぜると間隔が長さの2倍になり、**また破線になる**。
- **「少ない」と思ったらまず充填限界を計算する。** エルグは球面の1.3%しか
  なく、当時のピッチでは**上限が約115本**だった。歩きのバグを探す前に
  「そもそも何本入るのか」を出すこと。
- **継ぎ目は「隠す」より「無くす」。** セグメントを重ねて誤魔化すより、
  断面を経路に沿って**掃引**して1枚のストリップにする方が短く確実だった。
- **固定長の減衰は短い物を全部レンズにする。** 端の減衰を9ステーション固定に
  したら、18未満の尾根が端から端まで減衰＝またアーモンドになった。
  **減衰は対象自身の長さに比例させ、短すぎる個体は捨てる。**
- **滑らかさと配置の刻みを同じ数字で縛らない。** 歩幅はハッシュの制約
  （`RIDGE_PITCH` 未満は不可）だが、掃引の滑らかさは無関係。**補間して分離する。**
- **地球儀は上から見る。法線方向のスケールは見えない（§2-39）。** 針葉樹を
  「球を縦に伸ばす」で作っていたので、タイガが広葉樹に見えていた。
  **上から効く手がかりは「粒の細かさ」と「平面形」**であって高さではない。
  高さが効くのはリムと斜めから見たときだけ。
- **バリアントが形になった瞬間、ラウンドロビンのバケット割りはバグになる。**
  形が1種類なら i%N でよいが、種類ごとに形が違うなら**中身で振り分ける**。
- **不変条件は「守る」より「消せないか」を先に考える（§2-40）。**
  「ピッチ < 歩幅」という制約のせいで砂丘のピッチを広げられず、尾根が横に
  融合してヘビになっていた。**ハッシュ登録を歩行中から完成後に移すだけで
  制約自体が消えた。**
- **rad とワールド単位と px を、その都度どれで考えているか宣言する。**
  ピッチ 0.021 rad は「小さい」に見えるが、半径2の球では 0.042 ワールド単位で、
  幅 0.05 の断面より**狭い**。§2-38 でも同じ取り違えをしている。
- **最小サイズは「幅の何倍か」で決める。** 長さの絶対値で決めると、
  幅を変えた瞬間に最短の個体が菱形に戻る。

**マウントで新しく踏んだもの（全部 §2-31）:**

- **three の Euler 既定順 XYZ は Rx·Ry·Rz。** 回転を2つ持つグループは
  **順序を明示しないと意図した軸で回らない。** 小さい角度では見えないので、
  角度を大きくした瞬間に古いバグが牙を剥く。
- **テンプレートリテラル（シェーダ）の中にバッククォートを書くと
  コンパイルが通らない。** 前回の引き継ぎに書いてあったのに踏んだ。
  シェーダ内のコメントで識別子を囲みたくなったら、囲まずに書く。
- **ドローコールは「組み立て後」だけ測る。** `animate()` は球ができる前から
  回っているので、混ぜると min 12 / median 52 / max 163 になる。
  組み立て後だけなら 162/163 で安定。**`renderer.info.autoReset = false`。**
- **平板用に調整したマテリアルを曲面に着せると別物になる。** 銘板の
  metalness 0.55 / env 1.8 を弧に着せたら**蛍光オレンジ**になった。
- **バウンディングスフィアで「どこまで届くか」を測ると細長い物で嘘が出る。**
  雲は最大2.615なのに、球で測ると3.241と出た（＝環の半径を0.6も間違える）。
  **全頂点を変換して測ること。**
- **何かを動かしたら、その物が塞いでいた物を疑う。** 球を3cm上げただけで
  オーロラが漏れた。襟が遮蔽物として働いていたことは誰も書いていなかった。

**水系で新しく踏んだもの（§2-39 / §2-40 / §2-41）:**

- **「正しい」が4つ揃っても画面には出ない。** 湖は、標高が水で、塗りが水で、
  散布が木を立てず、シェルが上にあって、**それでも見えなかった**。
  白波・彫り込み段・メッシュ解像度・樹冠が順番に隠していた。
  **サブシステムが全部「正しく」動いた結果として消える**ので、
  どれ一つバグとしては見つからない。**マゼンタ差し替えで「どこに出るか」を
  撮るのが唯一の近道**（海シェルを不透明マゼンタにして「湖の footprint の
  2.8% にしかシェルが出ていない」が1枚で分かった）。
- **線を「セルの塗り」で描くと必ず破線になる。** D8 は対角に進むので、
  四角いセルは角でしか接触しない。**リンクを線分としてラスタライズする。**
- **可視量を「割合」で決めると格子解像度に依存する。** 同じ分位点で
  384→768 にしたら網の総延長が2倍になった。**セル数で決める量は
  格子でスケールさせる。**
- **伐開の到達距離は「対象＋樹冠1つ」。** 汀線や水路の縁で伐ると、
  正しく岸に立っている木が樹冠半径ぶん覆う。川は5倍、湖は1.9半幅。
- **`Object.defineProperty(..., {value, writable:false})` で季節を止めるな。**
  毎フレーム書いている `animate()` が例外を投げて**レンダループごと死ぬ**。
  前のフレームが残るのでスクショは一見成功する。**書き込みを捨てる setter に。**
- **全テクセルが引く場は必ずバケットに載せる。** 19湖の線形走査が
  塗り全体の4%だった。5度格子は `URBAN_BUCKET_LAT/LON` に既にある。

**引き続き有効な主要なもの（詳細は §2 各節）:**

- **作る前に「画面上で何pxになるか」を計算する。** **カメラが10.2になったので
  約102px/ユニット**（1280×760）。以前の「108〜110px」は9.6のときの値。
  **「描かれていない」と「0.3px幅で描かれている」は画面上で同じ**（§2-21）。
- **効果が微妙なものは、まず単色マゼンタに差し替えて「どこに出るか」を撮る。**
- **Poisson-disc 層は確率で間引いても減らない。距離（間隔）を変える**（§2-23）。
- **「修正済み」を疑う。** 砂丘のアーモンドは高さだけ直っていて
  平面形が楕円のまま残っていた（§2-23）。
- **風で流れる物の統計は1シードでは比較できない。16シード×惑星一周で平均**（§2-19）。
- **ある系統を直したら、同じ場を消費している別の系統を測り直す**（§2-19）。
- **THREE.Color は linear。遮蔽は掛ける、引かない**（§2-15）。
- **ビルド時に焼いた向き・位置は移流で狂う**（§2-17）。緯度は不変、経度は違う。
- **負の値の分数乗で NaN。three では NaN 行列は何も描かないので、
  バグが「意図した挙動」に化ける**（台風の静穏期がこれだった）。
- 明暗境界は動かない（§2-12）。**構図を触ったら必ず再確認。**
  指標は `|sun·viewDir|`（§2-31 に式と検算あり）。
- 球の画像A/Bは季節アニメで成立しない。机と平面展開図はA/Bできる。
- **加算合成の物を球の手前側に置くと、台座と机の上に光を塗る**（§2-29）。

## 5. 計測のやり方（これが本体）

**新しいセッションでは先に `npm ci` が要る。**

**まず gap-analysis §6「素の node でこのプロジェクトを回す」を読むこと。** 以下は
ブラウザが要る場合の話。

`buildTerrainTexture` も `buildClouds` も `buildSpecies` も `buildLandmarks` も
**WebGL を必要としない**。アプリ本体は swiftshader で**90〜110秒**かかるが、
**ルートに `_xx.html` ＋ `src/_xx.ts` を置いて直接 import すれば数秒で回る。**
変更前の版は `git show <rev>:src/clouds.ts > src/_cloudsOrig.ts` として
同時に import すれば同一プロセスで before/after を比較できる。

- **一時的な引数追加（シード等）は可。コミット前に必ず戻す。**
- インスタンスの「量」は `cbrt(|det|)`（行列式）がスケールに比例する。
- **「どこまで届くか」は全頂点を変換して測る。**バウンディングスフィアは
  細長い物で大きく外す（§2-31）。
- ドローコールは `renderer.info`。**`composer.render()` が info をリセットする**
  ので `renderer.info.autoReset = false`。**組み立て後のフレームだけ集めること。**
- 見た目は Playwright（`/opt/pw-browsers/chromium`、CommonJS なので
  `import pkg from '...'; const {chromium} = pkg;`）。**playwright 自体は
  プロジェクトに入っていないので、スクラッチ側に `npm i playwright` する**
  （`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`）。
  **`page.waitForFunction` は `(fn, arg, options)`。** 第2引数に options を
  渡すと既定の30秒のままになる（＝組み立てを待てない）。
  **`page.screenshot` にも `timeout` を明示。**
  拡大は「撮った png を `<img>` で拡大したページを撮り直す」のが速い
  （PIL は入っていない）。**`file://` は読めないので data URI にすること。**
- **フレーム内の位置は撮る前に角度で出せる。** カメラは
  距離10.2・画角40°・polar 0.405π・注視 y=0.15。ある点が画面の上端に
  かかるかは「視軸との角度 ≤ 20°」で判定できる（§2-31 で多用した）。
- **計測フックはコミット前に必ず外し、grep で確認する。**
