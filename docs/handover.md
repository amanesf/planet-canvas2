## 2. 次にやること

### 第一候補：彩度（レビュー第4位の残り半分）

**これだけ意図的に手を付けずに残してある。判断が要るから。**

階調の方（「球の上に深い影が一箇所もない」）は影の代用4種で解いた。
しかし**彩度が高いという指摘は未着手**で、実際レンダを見ると植生が
かなり鮮烈な黄緑〜エメラルドに寄っている。

**着手する前に §9 を読むこと。** この作品は過去に一度「全体的にトーンダウン」
して**洗いすぎた**と判断し、**意図的に彩度を上げ直した経緯がある**。
つまり「彩度を下げる」は記録済みの判断を巻き戻す方向。

推奨する進め方：

- 下げるなら**塗装（`terrain.ts` の基準色）ではなく植生インスタンスの側**から。
  レンダで飽和して見えているのは主に `species.ts` の `canopyClimate` が返す
  saturation と、その上に乗る季節ティント。塗装の彩度は §9 の判断の対象そのもの。
- **必ず平面展開図ではなく3Dレンダで判断すること。** 植生が地面を覆っているので、
  平面図の彩度は見えているものと一致しない（§2-16 で実際にこれを踏んだ）。
- 露出（`toneMappingExposure=1.9`）も候補だが、これを触ると夕暮れ帯（§2-12）と
  街の灯りの見え方が同時に動く。**単独で動かさないこと。**

### 第二候補：第3弾（気象場の一元化）

**費用対効果は依然としてここが最大。** `precipitationAt` /
`precipitationProfileAt` / `precipitationAtSeason` は完成しているのに
**消費側がゼロで、誰も使っていない**。G7（雲を気候から）・G34〜37（雨・雪・雷）・
G40・川の流量重みが全部ここにぶら下がっている。§3 の構造問題
（気象の発生源が一元化されていない）は土台ができただけで未解決のまま。

どちらを先にやるかは判断してよい。理由を述べてから進めること。

## 3. 前セッションで踏んだ地雷（同じ穴に落ちないこと）

**今回新しく踏んだもの:**

- **`THREE.Color` は linear 空間。`offsetHSL` で明度から定数を引くと、
  もともと暗い色は黒にクランプする。** 海岸の緑（linear 0.15）から 0.24 を
  引いたら全大陸に**硬い黒の輪郭線**が付いた。この作品が一貫して避けてきた
  デカール読みを事故で自分から作ったことになる。
  **遮蔽は「掛ける」もの。** 乗算なら暗い所も明るい所も同じ割合を失うので、
  原理的にキーラインが出ない。
- **強い darkening を気候ラスタに直結すると、最近傍の階段エッジ（§2-9）が
  フルコントラストで出る。強度を下げても矩形が薄くなるだけ。**
  引く「方向」をノイズでワープさせること。
- **`MultiplyBlending` は three では `premultipliedAlpha` が要る。**
  無しで使うと机の上に**白い紙**が乗る。コンソールが明示的に警告している。
- **塗装だけ暗くしても植生の下は見えない。** インスタンスが地面をほぼ完全に
  隠しているので、3Dで見るまで「効いていない」ことに気づけない。
- **ビルド時に焼いた向きは移流で狂う**（雲）。法線への最小回転は位置依存の
  ねじれを持つので、風で流れる物に固定の向きを焼くと1分以内に崩れる。
  方位角なら不変。
- **サブエージェントはレート上限で途中死する。** 実際に1組が
  「`tuftFor` を参照しているが存在しない」「フィールドを足したが誰も設定しない」
  状態で止まった。**成果は必ず自分で呼び出し側まで追うこと。**
  途中死した差分は patch に退避してから revert し、後で拾い直せばよい。

**従来からのもの（引き続き有効）:**

- **推測で判断せず計測フックを仕込む。着手前と完了後の両方で測る。**
- **計測フックはコミット前に必ず外し、grep で確認する。**
- 緯度経度の逆変換は `lon = atan2(z,-x)*180/π - 180`（-180 を忘れない）。
- 明暗境界は円盤上を掃かない（§2-12）。**構図を触ったら必ず再確認**（§2-18）。
- **球の画像A/Bは季節アニメで成立しない**（2枚で85%の画素が変わる）。
  ただし**机と平面展開図はA/Bできる** — どちらも時間に依存しないから。
  §2-18 で実際にこれを使って机の影を検証した。
- 並列エージェントはファイル所有を完全に分けること。
- 白波を「深度」でゲートしてはいけない（§2-10）。正しい量は海岸線からの距離。
- プレビューサーバは pkill と同じコマンドに混ぜない。並列時は `npx vite`。
- Playwright: `executablePath: '/opt/pw-browsers/chromium'`、
  `/opt/node22/lib/node_modules/playwright/index.js` は CommonJS なので
  `import pkg from '...'; const {chromium} = pkg;`。起動は swiftshader で
  50〜120秒ブレる。ハングではない。**負荷が高いと `page.screenshot` 自体が
  既定の30秒でタイムアウトするので `timeout` を明示すること。**

### 速い計測のやり方（今回作った）

`buildTerrainTexture` などは **WebGL を必要としない**（canvas 2d と画像だけ）。
アプリ本体を起動すると swiftshader で50〜120秒かかるが、
**ルートに `_measure.html` ＋ `src/_measure.ts` を置いて terrain を直接 import
すれば数秒で回る。** さらに `git show HEAD:src/terrain.ts > src/_terrainBefore.ts`
として**変更前後の両方を同時に import すれば、同一プロセスで before/after を
そのまま比較できる。** 今回の計測はほぼ全部これ。**使い終わったら消すこと。**

ドローコールと三角形数は `renderer.info` で測れるが、
**`composer.render()` は最後のフルスクリーンパスで info をリセットする。**
`renderer.info.autoReset = false` にして自分で `reset()` すること
（でないと `calls:1` と出て途方に暮れる）。

## 6. 未消化で残っている大物

着手時は §2 の該当節を必ず読むこと。

- **降水量プロキシの消費側がゼロ**（第3弾。上記 §2 第二候補）。
- **川がほぼ動いていない**（§2-8）。陸地セルの12.6%がシンク。
  **直すときは堆積扇の時限爆弾に注意** — `deltaCoast` がアマゾンで0.907
  あるので、水系を直した瞬間に砂色が盆地を3,000km内陸まで塗る。§2-8 に対処法。
- **都市の実体化**（G43〜G46）。ただし**186都市のうち26都市の中心座標が
  標高ラスタ上で水**なので、建物を正確な座標に置くと海に建つ（§2-11）。
- G5 地域アイコン、G6 砂丘の実座標配置、第6弾 波の作り直し。
- **雲の材質感**（§2-17 の残り）。シルエットの階層と櫛通しは入ったが、
  ズームすると「毛羽立った綿」ではなく「滑らかな白い小石」に見える。
  セグメントを増やすかハロー方式を開け直すかだが、**ハローは灰色の輪という
  最悪の失敗を一度直した経緯がある**（`clouds.ts` 冒頭）。当てずっぽうで触らないこと。
- **鏡面は海シェルにしか無い**（§2-18）。陸は意図的にマット（roughness 0.97）
  なので、映り込みが大陸の上に来る回転位相ではハイライトが完全に消える。
  気になるなら球マテリアルに非常に弱い同じ項を足すことになるが、
  「岩だけがマット」は既存の明示的判断なので、勝手に覆さないこと。
